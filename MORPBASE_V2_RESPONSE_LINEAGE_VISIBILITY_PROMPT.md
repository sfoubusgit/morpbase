# MorpBase V2 Response Lineage Visibility Prompt

## Goal

Define the first restrained response lineage visibility slice for the coded V2.

This is not a prompt for analytics, public metrics, or challenge systems.

It is a prompt for the smallest calm layer that proves:

- public workflow results can visibly carry consequences
- those consequences stay readable as object life
- and response visibility can exist without turning MorpBase into tracking software

## Starting Point

The coded V2 already has:

- private creation and return loops
- public circulation
- continuation invitations
- playful `make your own version` invitations

What it still lacks is:

- a clearer way to show what a public result has actually sparked

## Main Questions

### 1. Product Meaning

- What should response lineage visibility mean in MorpBase?
- Why is visible consequence stronger than visible metrics?

### 2. Object Fit

- Which public objects should get this first?
- should the first slice attach mainly to public workflow results?

### 3. First Slice Restraint

- What is the smallest first slice that proves the idea?
- where should it appear first?

### 4. Discipline

- What keeps this calm and object-led?
- What would make it drift into analytics, dashboards, or challenge logic?

## Output Format

Write the result as:

1. `Purpose`
2. `What Response Lineage Visibility Should Mean`
3. `Where It Should Attach First`
4. `What The First Slice Should Add`
5. `What It Must Not Become`
6. `Success Criteria`

## Guardrails

- do not build public metrics dashboards
- do not create scorekeeping
- do not create rankings or challenge logic
- keep the first slice tied to real public objects
- make the result strengthen object life, not abstract tracking
