# MorpBase V2 Prototype Execution Workflow Prompt

You are analyzing **MorpBase V2** as a **completely new rebuilt product in a new project folder**, not as a refinement of V1.

Your task is to define the **actual execution workflow** for the V2 prototype phase.

This phase comes **after** the experience-prototyping plan has already established:

- which slices matter most
- what they need to prove
- and in what sequence they should broadly be validated

This prompt is not about deciding whether to prototype.
It is about determining **how to actually run the prototype phase in a disciplined way**.

## Core Context

The governing references now are:

- `MORPBASE_V2_FOUNDATION_FREEZE.md`
- `MORPBASE_V2_PRODUCT_BLUEPRINT.md`
- `MORPBASE_V2_INTERACTION_BLUEPRINT.md`
- `MORPBASE_V2_TERMINOLOGY_MICROLANGUAGE_FREEZE.md`
- `MORPBASE_V2_DESIGN_UNIVERSE_PREPARATION.md`
- `MORPBASE_V2_EXPERIENCE_PROTOTYPING_PLAN.md`

You must treat those as constraints.

The strongest current prototype slices are:

1. core first-use `Workspace`
2. `Memory` continuation
3. `Community` circulation
4. `Continuity` activation
5. shell / hierarchy synthesis

## What This Workflow Must Decide

You must determine:

- what concrete prototype artifacts should be produced
- what order they should be built in
- what fidelity each artifact should use
- what each artifact must prove before the next one starts
- what the review / gate moments are
- when prototype work is strong enough to hand off into implementation planning

## Critical Constraints

- Treat V2 as a **fresh rebuild**
- Do **not** reopen foundation or blueprint debates by default
- Do **not** try to prototype everything at the same fidelity
- Do **not** produce a vague “make some mockups” workflow
- Do **not** make the workflow so rigid that learning cannot change sequence locally
- Do **not** jump into technical implementation planning too early

## Method

### 1. Start with real-life prototype execution pressures first

Write at least 5 realistic execution pressures such as:

- needing to validate first-use before visual polish swallows the problem
- needing to prove Memory is a second pole before public/community work gets too much attention
- needing to test Community integration without building a whole public platform
- needing to keep Continuity honest and lightweight
- needing to know when a prototype slice is “done enough” to move on

For each, explain what workflow discipline it demands.

### 2. Translate the prototype plan into execution tasks

For each major slice, define:

- the prototype artifact(s)
- the prototype fidelity
- the core validation question
- the acceptance gate

### 3. Define the execution sequence

Be explicit about:

- what should be built first
- what depends on what
- what can be parallelized lightly
- what must stay sequential

### 4. Define review/gate behavior

For each major phase, define:

- what review should happen
- what would require iteration
- what would allow the next phase to begin

### 5. End with a handoff judgment

State:

- what the prototype phase should produce at the end
- and what conditions must be satisfied before implementation planning begins

## Output Requirements

Write the result as:

`MORPBASE_V2_PROTOTYPE_EXECUTION_WORKFLOW.md`

Structure it with:

1. Executive Conclusion
2. Real-Life Prototype Execution Pressures
3. Prototype Artifacts By Slice
4. Execution Sequence
5. Review And Gate Criteria
6. What Can Iterate vs What Must Stabilize
7. End-State Of The Prototype Phase
8. Readiness For Implementation Planning
9. Final Judgment

The result should be practical, disciplined, and concrete enough to guide the actual prototype work without drifting into implementation.
