# MorpBase V2 Shell Navigation Hierarchy Prompt

You are deciding the shell and navigation hierarchy for MorpBase V2.

This is a whole-product V2 decision, not a Builder-only decision.
This is for a fresh rebuild in a new project folder.

The goal is not to preserve V1 navigation.
The goal is to decide how the full V2 product should be structured visibly and hierarchically.

## Already Locked

Respect these truths:

- V2 is a true successor, not a lighter side product
- the heart is reusable prompt-workflow authoring around a live workspace + Prompt Preview loop
- V2 must be one integrated product, not several equal mini-products
- Workspace is the dominant center
- Memory is the strong second pole
- Continuity and Community are real product realms
- Profile is a light creator/account surface
- first-wave must not make every realm equal again
- first-wave must also not hide the full MorpBase ambition so much that the product feels smaller than it really is

Also respect the strongest current synthesis:

- `Workspace as the dominant center`
- `Memory as the strong second pole`
- `Continuity and Community as real but hierarchically lighter realms`
- `Profile as a light creator surface`

## Working Rule

Use this method:

1. real-life usage drafts first
2. compare concrete shell / navigation hierarchy candidates
3. then choose the strongest one, or a precise synthesis

## Main Goal

Decide:

- what is truly top-level in the V2 shell
- what is secondary but still visible
- what is grouped inside what
- how Memory should behave as a realm
- how visible Continuity and Community should be in first-wave
- what the default entry and shell emphasis should be

## Real-Life Usage Drafts First

Before deciding, create at least 5 realistic product-shell usage drafts:

1. first-time user entering V2 and making a first result
2. returning user reopening saved work
3. user intentionally going to reusable sources/context
4. user later entering continuity/identity intentionally
5. user publishing / discovering / importing through community

Use those drafts to judge the shell candidates.

## Candidate Shell Types To Compare

Compare at least these kinds of visible shell models:

- flat four-realm top nav
- dual-core shell with lighter secondary realms
- workspace/memory primary with "more" grouping
- primary nav plus secondary rail model
- any stronger hybrid that emerges from the usage drafts

## Questions You Must Answer

1. What should be in the top-level primary navigation in first-wave V2?
2. What should be visible but secondary?
3. Should Continuity be top-level in first-wave, secondary-visible, or grouped?
4. Should Community be top-level in first-wave, secondary-visible, or grouped?
5. How should Memory behave:
   - pure archive
   - full library
   - living memory hub
   - something else?
6. Where should reusable sources/context live visibly?
7. What should the shell hierarchy communicate emotionally?
8. What structure best avoids both:
   - V1 multi-center drift
   - and V2 under-signaling of MorpBase’s larger ambition?

## Hard Constraints

Do not let the answer become:

- V1 tabs with cleaner labels
- a workspace-only shell that hides the rest too much
- a flat realm architecture where everything looks equally mature
- community as a detached annex
- continuity as premature theater
- memory as a dead library tab

## Output Requirements

Write the result to:

- `MORPBASE_V2_SHELL_NAVIGATION_HIERARCHY_ANALYSIS.md`

Include:

- executive conclusion
- real-life usage drafts
- concrete shell candidates
- candidate comparison
- chosen shell hierarchy
- top-level vs secondary visibility decision
- Memory behavior decision
- Continuity visibility decision
- Community visibility decision
- strongest risks
- final recommendation

Be decisive, but question your assumptions before locking the result.
