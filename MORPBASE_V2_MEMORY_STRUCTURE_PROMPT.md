# MorpBase V2 Memory Structure Prompt

You are designing the internal structure of the `Memory` realm for MorpBase V2.

This is a whole-product V2 decision for a fresh rebuild in a new project folder.
This is not just an archive-tab redesign.
This is not a V1 Prompt Library cleanup.

`Memory` has already been judged to be:

- a strong second pole of the whole product
- a living memory hub
- the place where useful creative work stays alive and reusable
- the home for saved workflow outputs, quick captures, reusable sources/context, and later light continuity-linked traces

Your job now is to determine the actual internal structure of that realm.

## Already Locked

Respect these truths:

- Workspace is the dominant center of V2
- Memory is the strong second pole
- reusable sources/context live inside Memory, with contextual entry from Workspace
- Continuity is a real but lighter realm in first-wave
- Community is a real top-level realm
- V2 must avoid both:
  - V1-style multi-center drift
  - and under-signaling MorpBase's full ambition

Also respect:

- save/reuse must feel alive, not passive
- Memory must not become a catch-all junk room
- Memory must support both first-use usefulness and long-term repeat creation

## Working Rule

Use this method:

1. make real-life usage drafts first
2. compare multiple Memory structures seriously
3. then choose what works best, or combine

## Main Goal

Determine:

- what the internal primary sections of Memory should be
- what the default landing view of Memory should be
- how saved outputs, quick captures, reusable sources/context, imports, and light continuity traces should live together
- what should be a true section versus a filter/lens/metadata layer
- how Memory should connect back into Workspace

## Real-Life Usage Drafts First

Before choosing a structure, create at least 5 realistic Memory usage drafts:

1. user saves a strong first result and later returns to it
2. user reopens a saved result and branches from it
3. user captures a rough useful result quickly and wants to triage it later
4. user intentionally browses reusable sources/context to shape a new workflow
5. user imports something from Community and wants it to live naturally inside personal Memory

Optionally also consider:

6. later light continuity traces attached to saved outputs or reusable assets

## Candidate Structures To Compare

Compare at least:

- archive-centric structure
- library-centric structure
- object-type zoned structure
- flow-based memory hub structure
- any hybrid that emerges from the usage drafts

## Questions You Must Answer

1. What is the best overall internal structure for Memory?
2. What is the default landing view of Memory?
3. What are the main sections inside Memory?
4. Which things deserve their own sections, and which should only be lenses/filters/metadata?
5. Where do reusable sources/context live?
6. Where does Quick Save / rough capture live?
7. How should imported public objects from Community land inside Memory?
8. How should continuity-linked traces appear in first-wave?
9. How should Memory connect back into Workspace without becoming a separate dead zone?

## Hard Constraints

Do not let Memory become:

- a dead archive
- a giant library with weak internal meaning
- a catch-all dump of unlike objects
- a separate app competing with Workspace
- a top-level simulation of future continuity maturity

## Output Requirements

Write the result to:

- `MORPBASE_V2_MEMORY_STRUCTURE_ANALYSIS.md`

Include:

- executive conclusion
- real-life usage drafts
- candidate structures
- candidate comparison
- chosen Memory structure
- main sections
- default landing view
- section vs lens decisions
- Community import behavior
- continuity-trace behavior
- workspace connection logic
- strongest risks
- final recommendation

Be decisive, but question your assumptions before locking the result.
