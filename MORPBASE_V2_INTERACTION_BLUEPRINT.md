# MorpBase V2 Interaction Blueprint

## 1. Executive Conclusion

The strongest interaction model for MorpBase V2 first-wave is:

- **one guided but non-wizard product with object-driven handoffs and contextual depth**

This means V2 should not behave like:

- a sequence of detached tools
- a step-locking wizard
- a dashboard with many equal entry tasks
- or a management-heavy system that interrupts creation

It should behave like:

- **one calm creative product where the user is gently guided at the center, and deeper systems enter when the work actually calls for them**

The key interaction law is:

- `the center should stay active, while support layers enter contextually and transitions should carry object meaning with them`

So the strongest behavior model is:

- guide strongly in `Workspace`
- hand off naturally into `Memory`
- broaden intentionally into `Community`
- activate `Continuity` on purpose
- and keep the shell quiet but legible throughout

## 2. Real-Life Interaction Journeys

### Journey 1. New user starts the first workspace flow and reaches a keep-worthy result

Goal:

- act quickly
- trust what is happening
- feel that the result is worth keeping

What this demands:

- first-use guidance must narrow attention without trapping the user
- the authoring side must suggest the next move clearly
- `Prompt Preview` must respond live enough to build trust
- the keep/save moment must feel like the natural completion of a creative pass, not a detached library action

### Journey 2. Returning user branches saved work into a new live session

Goal:

- continue, not restart

What this demands:

- `Memory` must treat saved work as reusable starting points
- branch/reopen/use actions must be dominant and immediate
- re-entry into `Workspace` must preserve a sense of lineage rather than dumping the user into a blank state

### Journey 3. User imports a public reusable asset into Memory and then uses it in Workspace

Goal:

- turn public discovery into private creative leverage

What this demands:

- import must feel like adoption, not bookmarking
- imported objects must land in the right Memory pillar with origin context preserved lightly
- the next use step from Memory into Workspace must be obvious and low-friction

### Journey 4. Continuity-aware user activates a recurring entity into live work

Goal:

- apply sameness across work without editing the continuity truth inside the active workflow

What this demands:

- `Continuity` must support browse/select/apply behavior cleanly
- activation into `Workspace` must feel like bringing stable context into live work
- once activated, continuity should remain visible in the session without hijacking the main workflow

### Journey 5. Creator publishes from Memory and sees Community complete the loop

Goal:

- experience publication as an extension of real work, not a detached upload ritual

What this demands:

- publish actions in `Memory` must feel like promoting an object into public life
- `Publishing` must help frame and release, not recreate the object
- `Discover` and creator/public pages must make that object's new public life legible

These journeys strongly imply:

- the strongest interaction design problem in V2 is not inside isolated screens
- it is the quality of handoffs between them

## 3. Product Blueprint Restated As Interaction Problem

The product blueprint becomes this interaction problem:

- how do we make one asymmetrical product feel fluid and trustworthy without flattening it into equal modes?

In interaction terms:

- `Workspace` must feel like the active instrument
- `Memory` must feel like living continuation
- `Community` must feel like public circulation of real work
- `Continuity` must feel like reusable sameness entering work intentionally

So the interaction blueprint must solve:

### 1. Attention hierarchy

- where the user should focus now
- what can stay quiet
- what can wait

### 2. State continuity

- how actions in one realm create meaningful next states in another

### 3. Context preservation

- how users move without feeling they have lost what they were doing or why it matters

### 4. Calm depth

- how the product remains deep without constantly surfacing all of its depth at once

## 4. Interaction Behavior By Screen Family

## 4.1 Workspace

### User intention

- shape a live result
- watch it become clearer
- decide when it is worth keeping

### Dominant actions

- choose / refine inside the current workflow block
- inspect the live `Prompt Preview`
- move forward, revisit, or tighten
- keep/save the result

### State transitions

- first-use starts in a guided active state
- each block moves from blank -> directed -> tuned
- phases move from untouched -> active -> shaped -> refined
- the session becomes keep-worthy when the user has enough coherence and confidence, not when a checklist is exhausted

### Contextual reveals

- support/context systems should appear as purposeful side entries
- not as constant competing panels
- reusable assets or continuity activation should enter when clearly relevant to the current session

### Key feedback loops

- every meaningful authoring action should reflect in `Prompt Preview`
- `Prompt Preview` should confirm progress without becoming a control overload surface
- the keep/save pathway should become more prominent as the session becomes stronger

### Interaction note

- `Workspace` should feel guided, but never locked
- the user should feel invited forward, not marched forward

## 4.2 Memory

### User intention

- keep
- reopen
- branch
- reuse
- publish

### Dominant actions

- open a kept result
- branch into new live work
- use a reusable asset
- promote or clean a capture
- publish eligible work

### State transitions

- kept work becomes a reusable object, not a dead record
- captures can move from rough -> useful -> kept/published
- imported public objects become first-class personal objects in the correct pillar

### Contextual reveals

- origin context for imported objects should be visible but light
- continuity-linked traces should enrich objects without replacing their main identity
- publish signals should appear strongest where an object has clear public potential

### Key feedback loops

- actions in Memory should create clear next states:
  - branch to Workspace
  - publish to Community
  - inspect continuity in Continuity

### Interaction note

- Memory should feel like active continuation, not static storage

## 4.3 Continuity

### User intention

- manage recurring sameness
- understand recurrence through work
- activate continuity in live sessions

### Dominant actions

- browse recurring entities
- inspect a specific entity
- see appearances through work
- activate the entity into Workspace

### State transitions

- entities move between unselected -> inspected -> activated
- appearances connect the entity to real kept work
- activation produces a live continuity state in Workspace without altering entity truth there

### Contextual reveals

- continuity lineage should appear when inspecting entities or continuity-linked work
- higher-order continuity relationships should remain minimal or hidden in first-wave

### Key feedback loops

- activating continuity should immediately clarify what changed in Workspace
- viewing an appearance should create a meaningful route back into Memory or the originating work

### Interaction note

- Continuity should feel concrete and applied, not archival and not literary

## 4.4 Community

### User intention

- discover useful public objects
- understand creators through real work
- publish objects into public circulation
- import useful public objects back into personal use

### Dominant actions

- scan and open from `Discover`
- switch between public object lenses
- explore creator practice
- publish from kept objects
- import/adopt public objects

### State transitions

- published objects move from private value -> public circulation
- discovered objects move from public view -> private Memory via import
- creator exploration deepens the object context without breaking the circulation loop

### Contextual reveals

- creator context should be present on public cards/pages, but not overpower object usefulness
- freshness/public life signals should stay lighter than the objects themselves

### Key feedback loops

- publishing should create visible public state
- importing should produce immediate private placement and next-use clarity
- creator following/discovery should create return energy without social-feed drift

### Interaction note

- Community should feel alive, but never scroll-hungry

## 4.5 Shell

### User intention

- know where they are
- move intentionally
- not feel overwhelmed

### Dominant actions

- enter a primary realm
- switch between primary realms
- access Continuity when needed
- access Profile only when needed

### State transitions

- active realm state should be clear and calm
- `Workspace` and `Memory` should carry the strongest lived emphasis
- `Community` should feel fully real but more intentional
- `Continuity` should feel visible but lighter

### Contextual reveals

- contextual realm-entry cues inside screens should often matter more than shell jumps

### Key feedback loops

- the shell should reinforce the strongest product movements:
  - Workspace <-> Memory
  - Memory -> Community
  - Community -> Memory
  - Continuity -> Workspace

### Interaction note

- the shell should help orientation without competing for attention

## 5. Cross-Product Transition Behavior

## Workspace -> Memory

Should feel like:

- preserving a result that has become worth keeping

Behavior:

- triggered from a clear keep/save moment
- preserves enough session meaning that the saved object feels like a continuation of live work
- should strengthen the user's sense that progress became durable

## Memory -> Workspace

Should feel like:

- returning to active creation from something already meaningful

Behavior:

- branch, reopen, or use actions should be immediate
- the launched session should feel derived, not blank
- source object context should be lightly preserved

## Memory -> Community

Should feel like:

- giving private value a public life

Behavior:

- publish entry should start from the object, not from a blank form
- public framing should be a refinement layer, not full re-authoring

## Community -> Memory

Should feel like:

- adopting public value into personal practice

Behavior:

- import should create a clear landing place
- the next action after import should be obvious:
  - inspect in Memory
  - use/branch in Workspace

## Continuity -> Workspace

Should feel like:

- bringing stable sameness into live work

Behavior:

- activating an entity should create a visible session state
- Workspace should acknowledge the active continuity context without making it the main task

## Memory -> Continuity

Should feel like:

- understanding recurrence through preserved work

Behavior:

- continuity-linked work in Memory should provide a meaningful drill-in into the relevant entity or appearance view

## 6. Interaction Guardrails

### 1. No wizard lock-in

Guidance must never trap the user in a rigid sequence.

### 2. No dead-end keeps or imports

Saving or importing must always imply a meaningful next state.

### 3. No support-system interruption of the center

Support systems should enter Workspace contextually and quietly.

### 4. No public behavior that mimics a generic feed

Freshness must support circulation, not become the point of the product.

### 5. No continuity abstraction without work evidence

Continuity interactions must stay grounded in entities and their appearances through work.

### 6. No shell behavior that overstates secondary realms

The shell must preserve asymmetry through behavior, not just labels.

## 7. Remaining Interaction Risks

### Risk 1. Workspace guidance becoming too form-like

If the guided first-flow layer feels like a questionnaire, the center weakens.

### Risk 2. Memory becoming too management-heavy

If Memory interactions feel like filing instead of continuation, the second pole weakens.

### Risk 3. Continuity feeling too passive

If Continuity does not visibly affect live work or explain recurrence well, it will feel decorative.

### Risk 4. Community import/publish loops feeling too thin

If private-public transitions are weak, Community will feel detached.

### Risk 5. Transition context loss

If users cross realms and lose why they came or what object they are acting on, V2 will feel fragmented despite strong structure.

## 8. Readiness For Next Phase

The interaction blueprint is now strong enough to move into:

- **terminology and micro-language freeze**
- and immediately after that:
- **design-universe preparation** or **experience prototyping**

My judgment on order is:

1. terminology/micro-language freeze
2. design-universe preparation
3. experience prototyping

Why:

- the interaction model is now strong enough
- but the product still needs tighter behavioral language before visual and prototype work

## 9. Final Judgment

The strongest interaction blueprint for MorpBase V2 first-wave is:

- **a guided but non-wizard interaction model where Workspace remains the active center, Memory turns results into continuation, Continuity enters through applied activation, Community completes the private-public loop, and all major transitions preserve object meaning across realms**

That is strong enough to stop broad behavioral speculation and move into terminology freeze and then design/prototype work.
