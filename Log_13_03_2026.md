## Project understanding

The project was identified as a React + Vite app centered around a structured prompt-building workflow.

Key architectural understanding:
- main app shell: `src/ui/App.tsx`
- prompt engine: `src/engine.ts`
- prompt pipeline modules in `src/modules/*`
- data loading from `src/data/*`
- Supabase-backed private stores for auth, prompts, pools, working sets, and profiles
- local/community hub data still partly stored through local hub stores

Important verification caveats discovered:
- tests were blocked in this environment earlier by sandbox/esbuild behavior
- `npm.cmd run type-check` was already failing before these changes because `tsconfig.json` includes `vite.config.ts` while `rootDir` points to `src`

## Tester feedback analysis

A tester chat and screenshots were analyzed in depth.

Main conclusions:
- the tester did not clearly understand what MorpBase is
- the app exposed too many concepts too early
- the tester interpreted the app as something like a prompt combinator or context organizer
- Working Sets caused confusion
- there were real broken-feeling states:
  - blank Builder steps
  - raw `INVALID_ATTRIBUTE` behavior
  - Working Set ambiguity

Core interpretation:
- the problem was not only bugs
- it was also product clarity, feature hierarchy, onboarding, and mental-model mismatch

## Product concept decisions

We chose an iterative, planning-first approach before further implementation.

Locked core product framing:
- MorpBase helps users build prompts from reusable pieces instead of rewriting them from scratch
- Builder is the first-use center of the app
- Freeform Prompt is optional support, not the main workflow
- Working Sets are focused prompt kits
- Pool Hub is a community layer

Locked product ladder:
- Core: Builder, Prompt Preview, Copy Prompt
- Reuse: User Pools, Prompt Library
- Focus: Working Sets
- Community: Pool Hub, public profiles, public/cloud sharing

## Pool Hub visibility issue

### Problem raised

A real user registered for MorpBase, but could not be found in Pool Hub.

### Investigation result

Before the fix:
- Pool Hub creator/user search was effectively built from Hub uploads
- public profiles were only used to enrich upload-derived creator entries
- registration alone did not make a user visible there

### Product decision

All users should be visible in Pool Hub, independent of whether they have uploads.

### Implemented solution

Files changed:
- `src/engine/authStore.ts`
- `src/ui/components/PoolHubPage.tsx`

Main changes:
- when a user is ensured/authenticated, a default `public_profiles` row is created if missing
- Pool Hub user search now includes all public profiles, including users with `0 uploads`
- Pool Hub copy was updated from creator-only wording to broader user-focused wording
- zero-upload profiles now show a friendly `No Hub uploads yet.` state
- public profiles reload on login-state changes

Important runtime note discovered:
- older users registered before this change may need to log in again once so the default public profile gets created

### Bootstrap admin rule

Current rule:
- if `admin_users` has rows, only those users are admins
- if `admin_users` is empty, the first registered user in `public.users` is treated as admin

This was discussed explicitly, and the first user was identified as the admin in the current setup.

Recommendation given:
- explicitly insert the real admin into `admin_users` later so the system no longer depends on the bootstrap fallback
