# MorpBase V2 Public Card / Preview Grammar Analysis

## 1. Executive Conclusion

The strongest public card grammar for MorpBase V2 is:

- **a shared utility-rich object card with a type-specific core**

This means a MorpBase public card should not be treated as:

- a social feed post
- a gallery tile
- a marketplace listing
- or a mini public object page

It should be treated as:

- **a scanable public object surface that quickly communicates identity, usefulness, creator grounding, and next action**

The key judgment is:

- MorpBase public cards need one recognizable shared language
- but the middle of the card must clearly separate:
  - `Public Workflow Results`
  - from `Public Reusable Assets`

So the winning model is:

- one shared card grammar
- with a type-specific usefulness core
- and light context adaptation by surface

That is the strongest way to make the public layer feel coherent without making every public object look the same.

## 2. Real-Life Usage Drafts

### Draft 1. User scans Discover quickly for something worth opening

Goal:

- decide in seconds what deserves attention

What this demands:

- cards must scan fast
- object type must be obvious
- usefulness must appear early
- creator grounding must be present without taking over

### Draft 2. User compares multiple reusable assets on a creator page

Goal:

- understand what each asset can shape in future workflows

What this demands:

- reusable asset cards need stronger future-use language than result cards
- the card core must help compare shaping value, not just title and creator

### Draft 3. Creator sees ready-to-publish candidates in Publishing

Goal:

- judge which private objects are strong enough for public release

What this demands:

- cards need to express public readiness and usefulness clearly
- the grammar must still work in a management-oriented surface

### Draft 4. User wants to tell instantly whether something is a result or a reusable asset

Goal:

- avoid conceptual friction in Community

What this demands:

- type distinction must be built into the grammar itself
- not left to tiny badges or metadata rows alone

### Draft 5. User lands on a creator page and wants more from one public practice

Goal:

- move through many objects without losing creator context

What this demands:

- cards must support repeated browsing without becoming noisy
- creator presence must be lighter on creator pages than on Discover, but still coherent

### Draft 6. Later community vitality grows and cards need to show movement

Goal:

- preserve return energy later

What this demands:

- cards need room for light freshness or participation signals later
- but those signals cannot redefine the card into a social unit

These drafts strongly suggest:

- a shared card language is necessary
- usefulness must be core
- object type must be visible in the card body
- and surface-specific weighting matters

## 3. Candidate Card Grammars

### Candidate A. Gallery / Image-First Card

What it is:

- strong image/hero first
- title and metadata below

What it emphasizes:

- visual appeal
- browsing speed

What it gets right:

- strong scanability
- can feel premium

Where it fails:

- too image-dependent
- weak at expressing reusable value
- risks flattening object meaning into visual presentation

### Candidate B. Metadata-First Listing Card

What it is:

- title
- type
- creator
- metadata
- actions

What it emphasizes:

- information density
- practical browsing

What it gets right:

- clear
- easy to build

Where it fails:

- too dry
- too listing-like
- weak product identity

### Candidate C. Creator-Forward Social Card

What it is:

- creator header first
- object below
- light activity and interaction signals

What it emphasizes:

- creator presence
- social energy

What it gets right:

- feels alive
- strong creator continuity

Where it fails:

- too profile/social shaped
- weakens object-first circulation

### Candidate D. Utility-Rich Shared Object Card

What it is:

- object identity
- creator grounding
- usefulness expression
- clear action
- light metadata

What it emphasizes:

- public object value
- actionability

What it gets right:

- strong alignment with Community
- good scanability
- strong import/open behavior

Where it fails:

- if not carefully differentiated, both object types can still feel too similar

### Candidate E. Asymmetric Shared Grammar With Type-Specific Core

What it is:

- shared top and bottom grammar
- but the middle "why this matters" section changes by object type

What it emphasizes:

- coherence plus distinction

What it gets right:

- strongest type separation
- strongest cross-surface flexibility
- avoids generic-card sameness

Where it fails:

- requires discipline in wording and layout so the shared grammar still feels unified

## 4. Comparison

### Why Candidate A loses

Because MorpBase public value is not purely visual and cannot depend on hero imagery alone.

### Why Candidate B loses

Because it is too dry and too close to a generic product/library listing.

### Why Candidate C loses

Because it drifts too far toward creator-social logic and weakens the public object as the main unit.

### Why Candidate D is strong

Because it correctly centers usefulness and action around the public object.

### Why Candidate E wins

Because it keeps D's strong shared object logic while solving the most important remaining problem:

- the need for the two public object types to feel clearly different inside one shared system

So the strongest result is:

- **a shared utility-rich object card with a type-specific core**

## 5. Chosen Public Card Grammar

The chosen public card grammar is:

- **a shared utility-rich object card with a type-specific core**

More concretely:

- every public card should share one recognizable MorpBase object language
- but the center of the card must answer a different usefulness question depending on object type

For:

- `Public Workflow Results`
  - the card should communicate outcome value and branch/import value

- `Public Reusable Assets`
  - the card should communicate shaping value and future workflow influence

This is strongest because it makes public cards:

- coherent
- legible
- useful
- and distinct

## 6. Shared Section Grammar

The shared card grammar should be:

### 1. Object Identity Strip

Must answer:

- what is this?

Includes:

- title
- clear type signal
- compact visual identity/hero if available

### 2. Creator Grounding

Must answer:

- who made this?

Includes:

- creator name
- compact creator identity cue
- optional follow/creator entry on some surfaces

### 3. Type-Specific Usefulness Core

Must answer:

- why does this matter?

This is the most important section in the card.

### 4. Primary Action Cluster

Must answer:

- what can I do now?

Likely actions:

- `Open`
- `Import`
- `Use`
- `Branch`

depending on object type and surface

### 5. Light Supporting Signals

Must answer:

- what else should I know quickly?

Includes lightly:

- freshness
- public status
- continuity/event badges later
- other compact context cues

This section should remain light.

## 7. Object-Type Differences

### Public Workflow Results

The type-specific core should communicate:

- what kind of outcome this is
- why it is worth building from
- what sort of workflow value it offers

Its action bias should be toward:

- `Open`
- `Branch`
- `Import`

Its language should feel like:

- reusable outcome
- worthy public result
- something to continue from

### Public Reusable Assets

The type-specific core should communicate:

- what kind of future work this can shape
- why it is useful as reusable material
- what workflows or directions it supports

Its action bias should be toward:

- `Open`
- `Import`
- `Use`

Its language should feel like:

- shaping material
- reusable source of influence
- something to adopt into future workflows

## 8. Surface Variants

The same grammar should flex by surface:

### Discover Variant

Bias:

- strongest scanability
- stronger creator grounding
- stronger freshness cues

Use:

- object circulation
- quick recognition
- action into deeper pages

### Creator Page Variant

Bias:

- slightly lighter creator grounding, because creator context is already provided by the page
- stronger comparison value across many objects from one practice

Use:

- browsing one creator's body of work
- object-type lens continuity

### Publishing Variant

Bias:

- stronger readiness/public-life cues
- slightly stronger management-action cues
- lighter discovery/freshness emphasis

Use:

- judging candidates
- reviewing public objects
- managing release state

These should be variants of one grammar, not separate card systems.

## 9. First-Wave Guardrails

### 1. No generic cards

If the card could belong equally to any AI community site, it is too generic.

### 2. No type ambiguity

Users should not need careful reading to tell result vs reusable asset.

### 3. No metadata clutter

Cards should express value, not dump fields.

### 4. No mini-pages

Cards should invite opening deeper surfaces, not replace them.

### 5. No surface-specific reinvention

Discover, creator pages, and Publishing should share one family resemblance.

### 6. Prepare for visual distinctiveness later

The grammar should be strong enough now that a later custom MorpBase visual universe can make it unmistakable, rather than needing to rescue a weak structure.

## 10. Final Judgment

MorpBase V2 public cards should be:

- **scanable**
- **usefulness-first**
- **creator-grounded**
- **object-distinct**
- **cross-surface coherent**

So the strongest final answer is:

- **a shared utility-rich object card grammar with a type-specific usefulness core and light surface-specific weighting**

That is the cleanest repeatable surface language for making the V2 public layer feel coherent, legible, and product-shaped.
