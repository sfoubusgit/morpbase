# MorpBase V2 Phase A Workspace Prototype Brief

## 1. Executive Conclusion

Phase A should produce:

- **one low-fidelity first-use Workspace flow map**
- **one medium-fidelity interactive Workspace slice prototype**
- and **one small higher-fidelity key-frame set only if needed to validate atmosphere and hierarchy**

This phase is not trying to prove all of V2.
It is trying to prove one thing:

- **can a new user enter the real Workspace, understand what to do, trust the live Preview, and reach a meaningful keep/save moment quickly enough?**

The most important discipline in Phase A is:

- prototype the center
- keep support systems quiet
- validate flow and trust before polish

## 2. First-Use Validation Moments

### Moment 1. Arrival in the real Workspace

The prototype must prove:

- the product center is immediately legible
- the user understands where action happens
- the shell can remain present without stealing focus

### Moment 2. Seeing the guided first-flow layer

The prototype must prove:

- guidance narrows attention helpfully
- it does not feel like a lecture or a fake onboarding product
- it still feels like the real Workspace

### Moment 3. Making the first meaningful authoring choice

The prototype must prove:

- the first action feels obvious
- the workspace feels guided, not form-like
- the user feels they are shaping something real, not answering abstract prompts

### Moment 4. Trusting `Prompt Preview`

The prototype must prove:

- Preview is clearly related to the authoring actions
- the user can feel progress and output confidence early
- Preview is informative without becoming a control-heavy side dashboard

### Moment 5. Reaching the first `Keep` / `Save` moment

The prototype must prove:

- this moment feels earned
- the result feels worth preserving
- the transition toward `Memory` feels natural and meaningful

## 3. Phase A Prototype Scope

### In scope

- direct entry into the real `Workspace`
- shell present in first-use state
- guided first-flow layer
- a representative first-run authoring flow
- live `Prompt Preview` relationship
- emerging `Keep` / `Save` moment
- handoff cue toward `Memory`

### Core product question

- does the Workspace-first experience make V2 feel clear, guided, and distinct quickly enough?

### Why the scope is narrow

- if this slice fails, later Memory/Community/Continuity work will not rescue the product

## 4. Prototype Artifacts

### Artifact 1. Low-Fidelity Flow Map

Purpose:

- validate structure and state sequence before styling pressure enters

Should capture:

- entry state
- guidance state
- authoring progression
- Preview response relationship
- keep/save emergence
- handoff toward Memory

### Artifact 2. Medium-Fidelity Interactive Prototype

Purpose:

- validate the feel of the first-use Workspace slice

Should allow testing of:

- entering Workspace
- moving through the first guided flow
- seeing Preview respond
- arriving at a keep/save-ready state

### Artifact 3. Optional Higher-Fidelity Key Frames

Purpose:

- validate atmosphere and hierarchy if needed

Use only for:

- first impression
- Workspace + Preview relationship
- first keep/save state

Not for:

- full polished UI production

## 5. Low-Fidelity Flow Map

The low-fidelity flow map should include these states:

### State 1. Workspace Entry

What is visible:

- the real Workspace shell
- authoring area
- `Prompt Preview`
- broader product shell in background

What must be proven:

- clear center of gravity

### State 2. Guided First-Flow Layer

What is visible:

- first-use guidance inside Workspace
- narrowed attention toward the first meaningful authoring move

What must be proven:

- guidance feels embedded, not separate

### State 3. First Authoring Action

What is visible:

- the first active block/decision area
- Preview ready to respond

What must be proven:

- user knows what to do first

### State 4. Early Preview Trust

What is visible:

- output reaction to early shaping choices

What must be proven:

- Preview relationship is clear and useful

### State 5. Mid-Flow Confidence

What is visible:

- stronger shaped state
- clearer sense of where the workflow is heading

What must be proven:

- the user feels progress without checklist pressure

### State 6. Keep/Save Emergence

What is visible:

- a clear, stronger keep/save path
- enough output confidence to consider preserving the result

What must be proven:

- the first success moment feels meaningful

### State 7. Handoff Toward Memory

What is visible:

- the notion that the result becomes durable and can live on beyond the session

What must be proven:

- `Memory` already feels like the right next place, even if Memory itself is not fully prototyped yet

## 6. Medium-Fidelity Prototype Requirements

The medium-fidelity prototype should support:

### 1. Real Workspace entry

No fake onboarding mode.

### 2. Guided first-flow behavior

The prototype should show how guidance narrows focus without trapping the user.

### 3. Authoring -> Preview relationship

At least a representative set of authoring moves should visibly affect Preview.

### 4. Emergent keep/save state

The prototype should make it clear that the result becomes worth preserving through use, not by default.

### 5. Shell calmness

The shell should remain visible enough to imply full product depth, while keeping attention on the center.

### Medium-fidelity rule

This prototype should be interaction-real enough to test flow and trust, but not so detailed that visual polish hides weak behavior.

## 7. Out-Of-Scope For Phase A

These should stay out of scope:

- full Memory implementation/prototype depth
- full public/community flows
- continuity activation flows
- advanced Workspace support-system entry
- full block-set coverage
- final visual styling
- implementation planning

These are later slices.

## 8. Gate 1 Review Criteria

Phase A passes only if:

### 1. First-use feels fast and real

The user should feel that they are in the real product quickly.

### 2. Guidance feels embedded, not tutorial-like

The first-flow layer should help without sounding or feeling like a course.

### 3. `Prompt Preview` builds trust early

The output relationship should be understandable and motivating.

### 4. The first keep/save moment feels earned

It should feel like preserving meaningful work, not filing.

### 5. The shell preserves hierarchy

The broader product should remain visible but backgrounded.

### Gate 1 failure signs

If any of these are true, Phase A should iterate before Phase B:

- the Workspace feels like a form or questionnaire
- the first-use layer feels separate from the real product
- Preview feels too weak or too control-heavy
- keep/save feels like storage, not success
- the shell distracts from the center or makes realms feel too equal

## 9. Final Judgment

Phase A should begin with a low-fidelity flow map and a medium-fidelity interactive Workspace slice, aimed at proving the first-use center before any other part of V2 gains weight.

That is the strongest real starting point for the prototype program.
