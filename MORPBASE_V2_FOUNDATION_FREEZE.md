# MorpBase V2 Foundation Freeze

## 1. Executive Conclusion

This document freezes the strongest product truths of MorpBase V2 before blueprint work begins.

Its purpose is:

- to stop broad conceptual drift
- to protect what has genuinely earned stability
- and to make the next V2 phases more disciplined

The central freeze is:

- **MorpBase V2 is a workflow-centered creative product with a strong Workspace + Memory core, a disciplined Continuity layer, and a real but downstream Community circulation layer**

This is now the governing product truth.

## 2. Frozen Core Truths

These are now frozen.

### 1. V2 is a new product build

- V2 is a new project in a new codebase
- not a V1 refactor

### 2. Preserve the heart, not the old nouns

The non-negotiable heart is:

- prompt creation should behave like a reusable workflow, not a disposable text box
- repeated creative logic should become structured and reusable
- a live workflow session must remain central
- useful work should be preserved and reused later
- continuity across sessions matters

### 3. V2 is not a smaller side-product

- V2 must be stronger, clearer, and more product-real than V1
- not flatter or less ambitious in spirit

### 4. The product is asymmetrical

- V2 is not a balanced platform of equal realms
- it is one product with a dominant center and supporting layers

### 5. First-use must let the user feel MorpBase before explaining MorpBase

- no lecture-first onboarding
- no fake onboarding product
- no early realm overload

## 3. Frozen Product Hierarchy

The product hierarchy is frozen like this:

1. `Workspace` is the unmistakable center
2. `Memory` is the indispensable second pole
3. `Continuity` is a real but lighter support realm
4. `Community` is a real but downstream public circulation layer
5. the long-range horizon remains future-facing, not first-wave

This hierarchy must not be flattened in later work.

## 4. Frozen First-Wave Realms

These first-wave realm roles are frozen.

### Workspace

Owns:

- live workflow shaping
- live prompt workflow authoring
- the main active creative session
- the `Workspace + Prompt Preview` loop

### Memory

Owns:

- kept work
- reusable assets
- capture inbox logic
- the strong reuse/branch/reopen loop

### Continuity

Owns:

- recurring entities
- their recurrence across work
- first-wave continuity grounded in entities and appearances/lineage

### Community

Owns:

- public circulation of MorpBase objects
- Discover
- Creators
- Publishing
- import/export style private-public object flow

### Profile

Owns:

- utility/account/private creator control

It is not a co-equal product realm.

## 5. Directionally Frozen Areas

These are strongly set in direction, but still need blueprint/design decisions.

### Workspace structure

Directionally frozen:

- guided workflow authoring + persistent Prompt Preview
- benchmark workflow orientation

Not yet frozen:

- exact block layouts
- exact interaction choreography
- exact visual composition

### Memory structure

Directionally frozen:

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`

Not yet frozen:

- exact retrieval patterns
- exact home composition

### Continuity structure

Directionally frozen:

- continuity atlas model
- first live lane: `Characters`
- first-wave grounded in entities + appearances

Not yet frozen:

- exact internal labels
- exact UI emphasis of lineage vs entities

### Community structure

Directionally frozen:

- `Discover`
- `Creators`
- `Publishing`
- two public object types

Not yet frozen:

- exact vitality/freshness behavior
- exact page/card composition

### Shell

Directionally frozen:

- primary-visible:
  - `Workspace`
  - `Memory`
  - `Community`
- secondary-visible:
  - `Continuity`
- utility:
  - `Profile`

Not yet frozen:

- exact shell layout and visual behavior

### First-use

Directionally frozen:

- direct-to-workspace
- guided first-flow layer inside the real workspace
- first meaningful success should culminate in a keep/save moment

Not yet frozen:

- exact onboarding layer presentation
- exact timing of secondary reveals

### Naming

Top-level names are near-frozen:

- `Workspace`
- `Memory`
- `Community`
- `Continuity`
- `Profile`

Deeper labels remain blueprint-stage.

## 6. Flexible Areas

These remain intentionally flexible for blueprint/design work.

- exact screen compositions
- transition mechanics
- sub-surface names
- microcopy and action phrasing
- detailed block interactions
- public card/page presentation details
- continuity internal terminology below the top level
- visual hierarchy implementation
- future design-universe expression

These should be solved in blueprint/design phases, not re-elevated into foundation debates.

## 7. Explicitly Deferred Areas

These are explicitly not first-wave foundation requirements.

- `Shared Storylines`
- larger world/story continuity structures
- methodology systems
- challenge / reward systems
- broader continuity lanes beyond what the first proof truly earns
- any feature that requires equal-center expansion of the product

These remain future-facing horizon areas.

## 8. V2 Guardrails

Future V2 work must not violate these.

### 1. No equal-center drift

If a decision makes the product feel like several equal apps, it is wrong.

### 2. No V1 noun revival by default

Old V1 terms should not come back unless they earn it under the V2 product truth.

### 3. No explanation-through-internals

The product should reveal value through use, not through architecture vocabulary.

### 4. No continuity inflation

Continuity must stay lighter, concrete, and provable in first-wave.

### 5. No community drift into feed/platform logic

Community must stay object-circulation-based.

### 6. No coding the rebuild before blueprint discipline exists

The new codebase should not start before blueprint/design work is strong enough.

### 7. No generic-product flattening

Clarity must not be achieved by draining MorpBase of identity or ambition.

## 9. How Future Decisions Should Be Tested

Every future V2 decision should be tested against these questions:

1. Does this strengthen the `Workspace -> Memory` core loop?
2. Does this preserve the asymmetrical product hierarchy?
3. Does this keep first-use clear and fast?
4. Does this belong to first-wave, or is it horizon material?
5. Is this a foundation question, a blueprint question, or a design question?
6. Does this make MorpBase more product-real and more competitive than simpler prompt tools?
7. Does this introduce helpful clarity, or just another concept?

If a decision fails these tests, it should be revised or deferred.

## 10. Final Judgment

The V2 foundation is now strong enough to stop broad concept expansion and move into blueprint work.

The cleanest final statement is:

- **MorpBase V2 should now be treated as a frozen workflow-centered product foundation with a dominant Workspace, a strong Memory loop, a disciplined Continuity layer, and a real but downstream Community layer, with future work shifting from conceptual expansion into blueprint, design, and controlled build preparation.**
