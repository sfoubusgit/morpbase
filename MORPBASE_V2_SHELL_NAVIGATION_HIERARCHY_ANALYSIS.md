# MorpBase V2 Shell Navigation Hierarchy Analysis

## 1. Executive Conclusion

The strongest first-wave shell hierarchy for MorpBase V2 is:

- **a dual-core primary shell with secondary-visible realms**

More concretely:

- **primary top-level:** `Workspace`, `Memory`, `Community`
- **secondary-visible:** `Continuity`
- **light utility surface:** `Profile`

The most important nuance is:

- this is **not** a flat four-realm shell
- it is an **asymmetric hierarchy**

So the real shell message is:

- Workspace is the center
- Memory is the strong second pole
- Community is a real public layer
- Continuity is visible and legitimate, but not yet equal in shell weight

This is the best result because it avoids both major V2 failures:

- recreating V1’s equal-center drift
- and hiding too much of MorpBase’s full product ambition

## 2. Real-Life Usage Drafts

### Draft 1. First-time user entering V2

Goal:

- understand what MorpBase is
- enter the right place immediately
- make a first result

What this demands:

- one obvious home and dominant center
- no more than a few strong top-level choices
- memory visible but not competitive with the center
- continuity not demanded yet

### Draft 2. Returning user reopening saved work

Goal:

- move between current creation and reusable memory quickly

What this demands:

- Memory cannot be hidden
- Memory cannot feel like a passive library
- Workspace and Memory must feel like a real pair

### Draft 3. User intentionally going to reusable sources/context

Goal:

- find reusable shaping assets without thinking of them as a separate co-equal product

What this demands:

- sources/context should live inside Memory
- not as a top-level pillar of their own

### Draft 4. User intentionally entering continuity later

Goal:

- access continuity on purpose without feeling that it should have been understood from minute one

What this demands:

- Continuity should be visible enough to feel real
- but not shell-dominant in first-wave

### Draft 5. User publishing / discovering / importing through community

Goal:

- move into public circulation naturally

What this demands:

- Community should be a real visible realm
- not hidden too deeply
- and not treated as only a profile/public appendix

These drafts strongly suggest:

- Workspace and Memory need primary strength
- Community needs true visibility
- Continuity needs legitimacy without equal shell force

## 3. Candidate Shell Hierarchies

### Candidate A. Flat Four-Realm Top Nav

Top-level:

- Workspace
- Memory
- Continuity
- Community

Utility:

- Profile

Strengths:

- very complete
- clearly expresses total platform ambition

Weaknesses:

- too equal
- likely to recreate multi-center reading
- Continuity looks more mature than it should in first-wave

### Candidate B. Dual-Core Plus Secondary Rail

Primary top-level:

- Workspace
- Memory
- Community

Secondary persistent rail / lighter shell access:

- Continuity
- Profile

Strengths:

- strongest hierarchy
- preserves product ambition
- Continuity is real but not over-weighted
- Community stays visible as a true public layer

Weaknesses:

- requires careful visual design so secondary does not feel hidden or lesser in value

### Candidate C. Workspace / Memory / More

Primary top-level:

- Workspace
- Memory
- More

Inside More:

- Continuity
- Community
- Profile

Strengths:

- very strong anti-fragmentation
- easy first-use clarity

Weaknesses:

- Community becomes too buried
- Continuity risks feeling like an afterthought
- may under-signal the full MorpBase platform

### Candidate D. Workspace / Memory / Community / More

Primary top-level:

- Workspace
- Memory
- Community
- More

Inside More:

- Continuity
- Profile

Strengths:

- good public visibility
- still protects against flat equality

Weaknesses:

- "More" can become a junk drawer if not disciplined
- Continuity may feel hidden rather than intentionally secondary-visible

### Candidate E. Primary Nav Plus Layered Home

Primary top-level:

- Workspace
- Memory
- Community

Layered home/dashboard includes:

- visible Continuity entry
- profile presence
- product-wide quick jumps

Strengths:

- strong first-use clarity
- Continuity still visibly belongs to the product

Weaknesses:

- too dependent on the home/dashboard concept
- could blur the shell if the dashboard becomes another center

## 4. Candidate Comparison

### Why Candidate A loses

Because it is the clearest route back to equal-realm drift.
It is too flat for first-wave V2.

### Why Candidate C loses

Because it hides too much of the full-product ambition and weakens Community visibility.

### Why Candidate D is close but loses

Because `More` is a weaker structural answer than making the hierarchy explicit.

### Why Candidate E is interesting but loses

Because it makes too much depend on a home/dashboard layer that could become a competing center.

### Why Candidate B wins

Because it is the best balance of:

- clarity
- hierarchy
- ambition
- anti-fragmentation protection
- and first-wave realism

## 5. Chosen Shell Hierarchy

The chosen first-wave V2 shell hierarchy is:

### Primary top-level navigation

- `Workspace`
- `Memory`
- `Community`

### Secondary-visible persistent access

- `Continuity`

### Light utility surface

- `Profile`

The most important thing here is not the exact labels.
It is the hierarchy:

- core creation
- reusable memory
- public circulation
- continuity as a real but lighter realm

This is the strongest current shell for first-wave V2.

## 6. Top-Level Vs Secondary Visibility Decision

### Top-level primary

`Workspace`

- because this is the core product center and the front door

`Memory`

- because reuse is too central to MorpBase’s actual strength to be hidden

`Community`

- because public circulation must already feel like part of the product, not a hidden annex

### Secondary-visible

`Continuity`

- because it is real and important
- but not yet mature enough to carry equal shell weight in first-wave
- and too much shell prominence would risk premature identity theater

### Utility-level

`Profile`

- because creator/account identity matters
- but should not be a top-level creative realm

## 7. Memory Behavior Decision

`Memory` should behave as:

- **a living memory hub**

Not:

- a dead archive
- a plain library page
- a dumping ground for saved prompts

Memory should visibly contain:

- saved workflow outputs
- quick captures
- reusable workflow-shaping assets
- reusable sources/context
- later light continuity-linked traces

Its emotional role should be:

- the place where useful creative work stays alive and reusable

This is one of the strongest V2 differentiators.

## 8. Where Reusable Sources / Context Live

Reusable sources/context should live:

- **inside Memory**
- with contextual entry from Workspace

They should not have their own equal top-level shell weight in first-wave.

Why:

- they matter deeply
- but they are still subordinate to creation + reuse
- promoting them to equal top-level status risks recreating V1 drift

So the right relationship is:

- discover or manage them in Memory
- apply them from Workspace when needed

## 9. Continuity Visibility Decision

Continuity should be:

- **secondary-visible in first-wave**

That means:

- clearly present in the shell
- easy to intentionally enter
- visually recognized as part of MorpBase

But not:

- as heavy as Workspace
- as foundational as Memory
- as publicly active as Community

This is the cleanest way to respect both truths:

- Continuity is very important long-term
- first-wave should not over-stage it before the center and memory loop are proven

## 10. Community Visibility Decision

Community should be:

- **primary top-level in first-wave**

Why:

- the product should not look private-only
- community must feel integrated, not hidden
- public discovery and circulation are too important to bury under `More`

But Community should still be visually lighter than Workspace.

So top-level does not mean equal emotional weight.
It means:

- real realm
- visible route
- part of the main product

## 11. What The Shell Should Communicate Emotionally

The shell should communicate:

- this is one serious creative product
- creation comes first
- reuse is built in
- public circulation is real
- deeper continuity is here when you are ready

It should **not** communicate:

- several equal subsystems
- one small workspace plus random extras
- a hidden platform ambition

The best emotional feel is:

- `clear center, real depth, controlled expansion`

## 12. Strongest Risks

### 1. Secondary Continuity feeling hidden or downgraded

This must be solved through wording and visual legitimacy, not by making it top-level-equal too early.

### 2. Community feeling too heavy in first-wave

It should be visible and real, but not visually compete with Workspace as the emotional center.

### 3. Memory becoming too broad

If Memory becomes a catch-all with weak internal structure, the shell will be right but the realm will be wrong.

### 4. Reusable sources/context disappearing inside Memory

They must be integrated, not buried.

### 5. Profile leaking into creator-center territory

Profile should stay light and supporting.

## 13. Final Recommendation

The strongest current shell/navigation hierarchy for MorpBase V2 is:

- **Primary:** `Workspace`, `Memory`, `Community`
- **Secondary-visible:** `Continuity`
- **Utility:** `Profile`

with these critical meanings:

- Workspace = dominant creative center
- Memory = strong living second pole
- Community = integrated public circulation layer
- Continuity = legitimate but lighter first-wave realm
- Profile = creator/account surface

The cleanest final sentence is:

- `MorpBase V2 should use an asymmetric shell: creation first, memory second, community visible, continuity present but lighter, and profile kept supportive.`

That is the strongest current shell hierarchy for a complete MorpBase V2 without repeating V1’s equal-center drift.
