# MorpBase V2 Community Structure Prompt

You are designing the internal structure of the `Community` realm for MorpBase V2.

This is a whole-product V2 decision for a fresh rebuild in a new project folder.
This is not a rebrand of Pool Hub.
This is not a profile-page cleanup.
This is not a detached social layer.

`Community` has already been judged to be:

- a real top-level realm in first-wave V2
- the public circulation layer of MorpBase's core creative objects
- integrated with Workspace and Memory
- not allowed to collapse back into "Pool Hub plus profiles"

Your job is to determine the actual internal structure of that realm.

## Already Locked

Respect these truths:

- Workspace is the dominant center
- Memory is the strong second pole
- Community is primary top-level in first-wave
- Continuity is secondary-visible in first-wave
- Profile is a light creator/account surface
- community must revolve around the same creative objects the core product creates
- community must publish MorpBase objects, not detached community-only objects
- imported public objects should land naturally into personal Memory

Also respect:

- first-wave must not over-stage community richness before the core loop is proven
- but Community must still feel real, integrated, and worth having top-level visibility

## Working Rule

Use this method:

1. make real-life usage drafts first
2. compare multiple Community structures seriously
3. then choose what works best, or combine

## Main Goal

Determine:

- what the primary internal sections of Community should be
- what the default landing view should be
- how discovery, creators, publishing, and import fit together
- what should be its own section versus a filter/lens/metadata layer
- how public objects and creator identity should relate
- how Community connects back into Memory and Workspace

## Real-Life Usage Drafts First

Before choosing a structure, create at least 5 realistic Community usage drafts:

1. user discovers a useful public object and imports it
2. creator publishes a saved result or reusable asset publicly
3. user explores a creator and their public work
4. creator manages their public-facing work and presence
5. later public continuity-linked work begins to appear

## Candidate Structures To Compare

Compare at least:

- legacy hub-plus-profile structure
- object-type marketplace structure
- creator-led social structure
- integrated discover / creators / publishing structure
- any hybrid that emerges from the usage drafts

## Questions You Must Answer

1. What is the best overall internal structure for Community?
2. What is the default landing view?
3. What are the main sections inside Community?
4. Which things deserve true sections, and which should be filters/lenses/metadata?
5. How should public objects be organized?
6. How should creator identity fit:
   - inside Community
   - versus inside Profile?
7. Where should publishing management live?
8. How should import behave?
9. How should later continuity-linked public objects appear in first-wave and later?
10. How should Community connect back into Memory and Workspace without becoming detached?

## Hard Constraints

Do not let Community become:

- Pool Hub with broader nouns
- a detached social app
- creator profiles with weak object flow
- a giant marketplace with no sense of MorpBase's creative process
- a noisy feed that competes with Workspace as the product center

## Output Requirements

Write the result to:

- `MORPBASE_V2_COMMUNITY_STRUCTURE_ANALYSIS.md`

Include:

- executive conclusion
- real-life usage drafts
- candidate structures
- candidate comparison
- chosen Community structure
- main sections
- default landing view
- section vs lens decisions
- creator identity decision
- publishing decision
- import behavior
- continuity-linked public object behavior
- workspace/memory connection logic
- strongest risks
- final recommendation

Be decisive, but question your assumptions before locking the result.
