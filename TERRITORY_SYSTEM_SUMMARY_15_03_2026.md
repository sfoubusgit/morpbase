# Territory System Summary 15.03.2026

This document captures the cleanest current model for how `Pools`, shared sections, `Territories`, and `Builder` fit together inside MorpBase.

It is intentionally shorter than the longer Territory direction memo.

## Core model

The strongest current product model is:

- `Pools` = source libraries
- `Sections` = shared semantic layer
- `Territories` = composed creative spaces
- `Builder` = active exploration surface

This is the clearest successor direction to the older category-heavy `Working Sets` model.

## Pools

Pools are:
- themed source libraries
- reusable vocabularies
- lightly organized by shared sections

They are the source layer of the system.

Pools should not be treated as only flat fragment dumps anymore.

## Shared sections

Current leading section vocabulary:
- `Subjects`
- `Environment`
- `Props`
- `Lighting`
- `Mood`
- `Materials`
- `Style`
- `Composition`
- `Effects`

Important rules:
- not every Pool needs every section
- sections stay broad and lightweight
- sections are descriptive, not heavy bureaucracy

These sections are the semantic bridge between:
- Pools
- Territories
- Builder

## Territories

Territories are:
- named creative spaces
- composed from selected `Pool + Section` inputs
- saved for reuse
- activated inside Builder

Example:
- `Subjects` from `Salvador Dali Dark Theme Park`
- `Environment` from `Arcane Library Fantasy`
- `Lighting` from `Magic Effects`
- `Mood` from `Semi-Real Portrait Mood`

That composition becomes one active Territory.

## Builder

Builder is:
- the main creation surface
- the place where an active Territory is explored
- the consumer of selected section layers

The user should not manually reorganize selected Territory material for Builder.

The system should:
- understand section meaning
- merge selected sections
- map them into Builder automatically
- show the result coherently

## System flow

The cleanest current flow is:

1. create or expand Pools
2. organize them with light sections
3. compose a Territory from selected pool sections
4. activate the Territory in Builder
5. build prompts inside that focused creative space

## Why this is stronger than the old model

This avoids the earlier problems of:
- heavy Working Set administration
- category-bucket maintenance
- item-by-item cherry-picking as the main path
- multiple incompatible conceptual systems across the product

It keeps the product much more coherent.

## Current naming conclusion

`Working Set` should now be treated as a legacy term tied to the older model.

`Territory` is the leading future name because it better communicates:
- a creative space
- a focused world of exploration
- an active Builder mode

## Current product conclusion

The clearest future direction is:

`Territories built from shared pool sections and activated inside Builder.`

That is the most coherent system model reached so far.
