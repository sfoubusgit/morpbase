# MorpBase V2 Top-Level Shell Analysis

## 1. Executive Conclusion

The strongest top-level shell for MorpBase V2 first-wave is:

- **an asymmetric primary shell with secondary-visible continuity and utility-level profile**

More concretely:

- `Workspace`, `Memory`, and `Community` should be **primary-visible**
- `Continuity` should be **secondary-visible but persistent**
- `Profile` should be **utility-level**

The key judgment is:

- the shell must make the product feel complete
- without making all realms feel equally mature or equally central

So the right shell is not:

- a flat four-tab top nav
- a dashboard-first shell
- or a hidden/overflow-heavy shell

It is:

- a shell with one clear primary band
- one lighter but visible continuity entry
- and a utility layer kept separate from product hierarchy

## 2. Real-Life Shell Journeys

### Journey 1. First-time user enters the product and needs immediate orientation

Goal:

- know where to start
- understand the product hierarchy quickly

What this demands:

- `Workspace` must read as the obvious center
- the shell must show a small number of strong options
- the shell must not imply equal importance among all destinations

### Journey 2. Returning user moves quickly between Workspace and Memory

Goal:

- continue real work fluidly

What this demands:

- Workspace and Memory must both be primary-visible
- their active states and transitions must feel especially strong

### Journey 3. User intentionally enters Community without losing product-center awareness

Goal:

- use public circulation as part of the same product

What this demands:

- Community must be easy to enter
- but the shell should still preserve that Community is not the product's home center

### Journey 4. User notices Continuity and understands it is real but not primary

Goal:

- make Continuity feel legitimate without implying equal first-wave force

What this demands:

- Continuity must be persistently visible
- but it should be visually/structurally lighter than the primary band

### Journey 5. User moves between surfaces without the shell feeling busy or fragmented

Goal:

- preserve calm product identity

What this demands:

- the shell must not expose too many competing weights
- utility/profile behavior must stay separate from realm hierarchy

These journeys strongly suggest:

- V2 needs a shell that makes asymmetry visible, not just conceptually true

## 3. Candidate Shell Models

### Candidate A. Flat Top Navigation

Always visible:

- Workspace
- Memory
- Community
- Continuity
- Profile

What it gets right:

- simple
- familiar

Where it fails:

- too equal
- recreates the wrong product reading

### Candidate B. Left Rail With All Realms Equal

Always visible:

- all main realms in one vertical list
- profile/settings lower

What it gets right:

- clear
- product-like

Where it fails:

- still too equal
- visually overstates Continuity in first-wave

### Candidate C. Dashboard-Led Hybrid Shell

Always visible:

- Home/dashboard plus realm entry points

What it gets right:

- flexible
- overview-friendly

Where it fails:

- dashboard becomes another center
- weakens the "enter Workspace directly" principle

### Candidate D. Asymmetric Primary Band + Secondary Continuity Entry

Always visible:

- primary band:
  - Workspace
  - Memory
  - Community
- secondary persistent entry:
  - Continuity
- utility:
  - Profile

What it gets right:

- preserves product hierarchy clearly
- keeps Continuity visible without flattening
- gives Community true legitimacy
- keeps utility separate

Where it fails:

- requires careful design so secondary-visible does not feel hidden or decorative

### Candidate E. Primary Top Nav + More Menu

Always visible:

- Workspace
- Memory
- Community
- More

Inside More:

- Continuity
- Profile

What it gets right:

- simple
- strong first-use clarity

Where it fails:

- hides Continuity too much
- makes the product seem smaller than it is
- weakens one of the deliberate V2 choices

### Candidate F. Dual-Rail Shell

Always visible:

- top primary nav
- side contextual rail for secondaries and actions

What it gets right:

- expressive
- flexible

Where it fails:

- too heavy for first-wave
- risks shell complexity before visual language is even defined

## 4. Comparison

### Why Candidate A loses

Because it is the fastest route back to equal-center drift.

### Why Candidate B loses

Because even with good styling, it still communicates too much equality.

### Why Candidate C loses

Because it creates another product center that V2 does not need.

### Why Candidate E loses

Because it makes Continuity too hidden for the role we have now correctly defined for it.

### Why Candidate F is interesting but loses

Because it introduces too much shell machinery too early.

### Why Candidate D wins

Because it best expresses:

- primary strength
- legitimate secondary visibility
- and utility separation

So the strongest result is:

- **an asymmetric primary shell with secondary-visible continuity and utility-level profile**

## 5. Chosen Shell Model

The chosen shell model is:

- **primary-visible band + secondary-visible continuity entry + utility-level profile**

This should be interpreted as:

### Primary product band

- `Workspace`
- `Memory`
- `Community`

These are the strongest visible destinations.

### Secondary-visible realm

- `Continuity`

This should be always available, but visually lighter.

### Utility layer

- `Profile`

This should be clearly separated from the product-realm hierarchy.

The shell should make the product feel like:

- one coherent product
- with one dominant center
- one strong return zone
- one real public destination
- and one lighter but legitimate support realm

## 6. Primary / Secondary / Utility Visibility

### Primary-visible

These should have the strongest shell weight:

- `Workspace`
- `Memory`
- `Community`

Why:

- they form the strongest first-wave user loop
- they represent the most important direct destinations

### Secondary-visible

This should be visible but lighter:

- `Continuity`

Why:

- it is real and enterable
- but not equal in first-wave force

### Utility

This should be separated:

- `Profile`

Why:

- it supports the product
- but should not participate in realm hierarchy

## 7. Navigation Behavior

### Default entry

- `Workspace`

### Strongest return movement

- between `Workspace` and `Memory`

### Public-intent movement

- into `Community`

### Intentional support movement

- into `Continuity`

### Utility movement

- into `Profile`

The shell should therefore not just highlight destinations.
It should support the idea that:

- some movements are more central than others

The strongest active-state emphasis should likely belong to:

- `Workspace`
- `Memory`

with:

- `Community` still clear
- `Continuity` clear but lighter

## 8. Transition Emphasis

The shell should visibly support these transitions most strongly:

### 1. Workspace <-> Memory

This is the core product loop.

### 2. Memory -> Community

This is the strongest public release path.

### 3. Community -> Memory

This is the strongest public-to-private reuse path.

### 4. Continuity -> Workspace

This is the strongest continuity activation path.

These do not all need dedicated shell buttons.
But the shell and its surrounding product behavior should make them feel natural and expected.

## 9. Guardrails

### 1. No flat shell

If all main destinations feel equal, the shell is wrong.

### 2. No hidden Continuity

If Continuity disappears into overflow, the shell is wrong.

### 3. No dashboard center

If a product home becomes the true center instead of Workspace, the shell is wrong.

### 4. No profile inflation

If Profile starts reading like a public realm peer, the shell is wrong.

### 5. No shell busyness

If the shell needs too many layers, rails, or visible controls to explain itself, the shell is too complicated for first-wave.

## 10. Final Judgment

The strongest top-level shell for MorpBase V2 first-wave is:

- **an asymmetric shell with a primary-visible band for Workspace, Memory, and Community; a secondary-visible but persistent Continuity entry; and a utility-separated Profile**

That is the cleanest shell expression of the current V2 product truth and the safest way to preserve hierarchy without losing completeness.
