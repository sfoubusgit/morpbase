# MorpBase V2 Stage Checkpoint Reassessment Prompt

## Purpose

Run this prompt whenever MorpBase V2 reaches a real stage boundary.

Examples:

- after a major concept phase
- after a realm has been shaped
- after a prototype slice has passed
- after a broader whole-product view has been built
- before moving from one major phase into another

The goal is:

- stop momentum from becoming autopilot
- reassess the whole picture from a broader scope
- question what still holds and what may be wrong
- recombine the best parts of what has been learned
- watch for better options before going deeper

## Core Rule

Do not use this prompt to casually reopen everything.

Use it to answer:

- are we still on the strongest path?
- what did we learn that changes the picture?
- what should be corrected, recombined, frozen, or dropped?

This prompt is not for random doubt.
It is for disciplined stage reassessment.

## What To Reassess

Look at:

- the original intention of the stage
- the outputs created during the stage
- what changed in understanding
- what tensions or contradictions appeared
- whether the result still fits the frozen MorpBase V2 heart

Always ask:

- does this still feel like MorpBase?
- does this still feel integrated?
- does this still feel stronger than simpler alternatives?
- does this still feel like one product, not several islands?

Use the relevant governing docs first:

- `MORPBASE_V2_GOVERNING_SET.md`
- `MORPBASE_V2_FOUNDATION_FREEZE.md`
- `MORPBASE_V2_PRODUCT_BLUEPRINT.md`
- `MORPBASE_V2_INTERACTION_BLUEPRINT.md`
- `MORPBASE_V2_TERMINOLOGY_MICROLANGUAGE_FREEZE.md`
- `MORPBASE_V2_DESIGN_UNIVERSE_PREPARATION.md`
- `MORPBASE_V2_PROTOTYPE_EXECUTION_WORKFLOW.md`

Then use the stage-specific docs, prototypes, and review outputs that were created for the stage being reassessed.

## Questions To Answer

### 1. What clearly still holds?

Identify the strongest truths that survived the stage.

These are the things that should not be casually reopened.

### 2. What became weaker, shakier, or less convincing?

Look for:

- overbuilt concepts
- weak transitions
- generic feeling
- wrong weighting
- misleading terminology
- detached realm behavior
- prototype logic that looked correct but felt wrong

### 3. What new insight changed the picture?

Identify what the stage taught that was not clear before.

This is often the most important part.

### 4. What should be recombined?

Look for good parts that may belong together differently than before.

Examples:

- the right structure but the wrong weighting
- the right object model but the wrong surface
- the right realm but the wrong transition
- the right name but the wrong place

### 5. Are there better options now?

Do not ask this in a vague way.

Ask:

- given everything we now know, is there a better path than the one we are currently on?
- if yes, is it better enough to justify correction?

### 6. What mistakes or drift risks are visible now?

Look especially for:

- V1-style multi-center drift
- feature-local thinking
- generic app behavior
- overcopying outside references
- image-first drift
- continuity-theater
- community becoming detached
- over-abstract planning

### 7. What should happen next?

Choose one:

- continue
- continue with corrections
- tighten one slice before moving on
- recombine and rewrite part of the model
- pause and reassess at a higher layer

## Output Requirements

Write one stage-specific report with a clear name, for example:

- `MORPBASE_V2_<STAGE_NAME>_CHECKPOINT_REASSESSMENT.md`

The report must include:

1. executive conclusion
2. what still holds
3. what weakened or changed
4. key new insight
5. best recombinations
6. stronger alternative options, if any
7. visible mistakes / drift risks
8. corrected stage reading
9. final next-step recommendation

## Quality Bar

The result should help answer:

- should we trust the current direction more, or correct it now?

If the output only summarizes what already exists, it is not good enough.

If the output reopens everything without judgment, it is also not good enough.

The right result should be:

- honest
- integrating
- corrective when needed
- and strong enough to govern the next phase.
