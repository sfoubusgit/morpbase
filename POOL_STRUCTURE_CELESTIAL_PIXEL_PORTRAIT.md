# Pool Structure: Celestial Pixel Portrait

## Date

18 March 2026

## Purpose

This document translates the `Celestial Pixel Portrait` workflow and its IDP sets into an actual pool structure.

The goal is to define:

- the Pool's stable core
- the set-sensitive variation zones
- the sections that should exist
- the kinds of items each section should carry

This is the structural bridge between:

- concept
- IDP sets
- future implementation

## Pool Identity

Suggested pool name:

- `Celestial Pixel Portrait`

This should be treated as:

- a **primary identity pool**

not:

- a total content pool
- a single-image recipe

## Structural Design Goal

The pool must support:

- strong family identity
- multiple IDP sets
- many iterations
- compatibility with future secondary Pools

That means the Pool should be split into:

- stable-core sections
- flexible extension sections

## Stable Core Sections

These sections should preserve the shared workflow family:

- `Style`
- `Lighting`
- `Composition`

These should be the most disciplined parts of the pool.

## Flexible Extension Sections

These sections should create the variation space:

- `Subjects`
- `Mood`
- `Effects`

Optional future section:

- `Props`

These are the best attachment points for future secondary Pools too.

## Recommended Sections

### 1. Subjects

Role:

- carry archetype
- carry ornamental identity hints
- leave exact lore open

Should include:

- celestial heroine
- shrine maiden
- magical idol
- moon oracle
- occult pastel seer
- star guardian
- jeweled dream singer
- crescent witch
- ribboned charm maiden
- sacred lantern bearer

Design rule:

- subjects should suggest identity direction without fully locking the whole image

## 2. Style

Role:

- preserve family identity
- define the pixel-anime rendering core

Should include:

- luminous anime pixel portrait
- polished decorative sprite portrait
- pastel celestial pixel rendering
- soft crystalline highlight treatment
- ornate pixel detailing with clean silhouette readability
- high-fidelity anime sprite portrait
- glowing pastel sprite polish
- detailed ornamental pixel portrait
- dreamy polished pixel-face rendering
- delicate low-resolution fantasy portrait finish

Design rule:

- style entries should be stable enough that the workflow still reads as the same family across all IDP sets

## 3. Lighting

Role:

- preserve glow family
- support identity without taking over composition

Should include:

- pastel celestial glow
- radiant pink-white eye glow
- soft moonlit rim light
- pearl-white magical bloom
- luminous cyan-pink edge lighting
- sacred inner glow
- candy-tone magical highlights
- polished jewel-like light accents
- eerie pastel arcane glow
- soft starlight shimmer on the face

Design rule:

- this section should support all three sets without collapsing into one exact emotional tone

## 4. Mood

Role:

- create most of the set-level emotional variation

Should include cross-set variation such as:

### Shrine-leaning

- sacred serenity
- devotional calm
- celestial stillness

### Idol-leaning

- radiant charm
- polished sweetness
- luminous confidence

### Occult-leaning

- arcane mystery
- uncanny dream-focus
- eerie softness

Plus shared in-between moods:

- enchanted stillness

Design rule:

- mood is one of the most important iteration levers

## 5. Composition

Role:

- hold the stable portrait structure

Should include:

- centered symmetrical bust framing
- frontal sacred portrait composition
- hands presenting a glowing emblem
- shrine-like portrait symmetry
- head-and-shoulders magical icon framing
- face-centered portrait with decorative accessory spread
- balanced front-facing magical portrait
- symmetrical close bust crop
- icon-like portrait presentation
- ceremonial portrait framing

Design rule:

- composition should remain highly disciplined

## 6. Effects

Role:

- decorate the baseline identity
- open space for set-specific surface variation

Should include:

### Shrine-leaning

- celestial sparkles
- sacred glow dust
- floral light motes

### Idol-leaning

- radiant glitter accents
- charm-like shine particles
- jewel sparkle bursts

### Occult-leaning

- eerie pastel shimmer
- arcane dust motes
- crescent-like glow fragments

Plus shared:

- crystalline sparkle accents

Design rule:

- effects should enrich, not replace, the family identity

## Optional Future Section: Props

This section should be added only if needed.

It is a strong candidate for later compatibility work.

Examples:

- glowing crystal emblem
- jeweled charm focus
- sacred lantern core
- crescent sigil relic
- floral starlight talisman

Why optional:

- too much prop specificity too early could over-lock the workflow

## Mapping IDP Sets To Pool Structure

The three IDP sets should not each get fully separate sections.

Instead:

- they should read from the same overall pool
- but lean on different item families inside the flexible sections

### Celestial Shrine leans on

- Subjects: shrine, sacred, floral, ceremonial
- Mood: serene, devotional, celestial calm
- Effects: sacred sparkles, floral light motes

### Magical Idol leans on

- Subjects: ribboned, jeweled, charming, idol-like
- Mood: radiant, polished, sweet, confident
- Effects: glitter, jewel shine, charm sparkle

### Occult Pastel leans on

- Subjects: crescent, arcane, occult, dream-seer
- Mood: eerie, mysterious, uncanny-soft
- Effects: arcane shimmer, strange pastel glow fragments

## Secondary Pool Compatibility Strategy

This structure should remain compatible with future secondary Pools by leaving space mostly in:

- `Mood`
- `Effects`
- `Props`
- selected `Subjects` accents

More protected sections:

- `Style`
- `Lighting`
- `Composition`

This is important because the pool should act as:

- a stable identity host

not:

- an overstuffed closed system

## Recommended First Build Order

If we implement this as a real pool later, the cleanest order is:

1. define shared `Style`
2. define shared `Lighting`
3. define shared `Composition`
4. define set-sensitive `Subjects`
5. define set-sensitive `Mood`
6. define set-sensitive `Effects`
7. only then decide whether `Props` are needed

## Final Structural Conclusion

The `Celestial Pixel Portrait` pool should be built as:

- one shared primary identity pool
- with stable core sections
- with flexible extension sections
- with three selectable IDP set readings layered on top

That is the strongest structure for preserving:

- coherence
- iteration range
- future compatibility
