# MorpBase V2 Prototype Execution Workflow

## 1. Executive Conclusion

The strongest execution workflow for the V2 prototype phase is:

- **a gated five-slice prototype program with rising fidelity, strict review points, and one final synthesis pass**

This means the prototype phase should not be run as:

- a big batch of screens
- a parallel free-for-all
- or a generic mockup sprint

It should be run as:

- **a sequence of proof-building prototype slices**

where each slice validates one major part of the product before the next one carries more weight.

The core execution law is:

- **prototype the center first, prove the second pole second, validate public circulation third, keep Continuity honest fourth, and only then test the whole product as one stitched experience**

## 2. Real-Life Prototype Execution Pressures

### Pressure 1. First-use must be validated before visual polish hides structural weakness

Why this matters:

- if the first-use Workspace slice is weak, later polish will only hide the problem temporarily

What workflow discipline it demands:

- prototype the core Workspace slice first
- validate time-to-value, guidance, and Preview trust before broader product expansion

### Pressure 2. Memory must prove itself as a second pole early

Why this matters:

- if Memory still feels like storage, the product’s strongest differentiator weakens

What workflow discipline it demands:

- run the Memory continuation slice before heavy Community prototyping
- confirm branch/reopen/use feels central

### Pressure 3. Community must be tested as an integrated loop, not as an isolated destination

Why this matters:

- Community can look convincing in isolation while still feeling bolted on in practice

What workflow discipline it demands:

- prototype Community through publish/import loops, not browse-only surfaces

### Pressure 4. Continuity must remain disciplined

Why this matters:

- Continuity is the most likely realm to drift into premature complexity

What workflow discipline it demands:

- keep its slice narrowly focused on entity -> appearance -> activation
- do not prototype broader continuity worlds or narrative systems

### Pressure 5. The shell must prove hierarchy in lived experience, not just in mock diagrams

Why this matters:

- if the shell still feels like equal tabs, the whole V2 hierarchy collapses in use

What workflow discipline it demands:

- test shell/hierarchy explicitly through a stitched prototype, not by assuming earlier slices imply it

These pressures imply:

- sequence matters
- fidelity should rise gradually
- and review gates must stop weak slices from silently contaminating later ones

## 3. Prototype Artifacts By Slice

## Slice 1. Core First-Use Workspace

### Prototype artifacts

- low-fidelity flow map of first-use Workspace path
- medium-fidelity interactive Workspace prototype
- higher-fidelity key-frame or short stitched prototype for the first-use moment

### Core validation question

- can a new user enter the real Workspace, understand what to do, trust Preview, and reach a meaningful keep/save moment fast enough?

### Acceptance gate

- first-use feels guided but not rigid
- Preview relationship is clear
- keep/save feels like a real creative completion

## Slice 2. Memory Continuation

### Prototype artifacts

- medium-fidelity Memory structural prototype
- focused interaction prototype for branch/open/use
- stitched transition prototype for Workspace -> Memory -> Workspace

### Core validation question

- does Memory feel like living continuation rather than storage?

### Acceptance gate

- saved work feels reusable
- branch/open/use are dominant and intuitive
- transition back into Workspace preserves meaning

## Slice 3. Community Circulation

### Prototype artifacts

- medium-fidelity publish-from-Memory prototype
- medium-fidelity Discover/public object/import loop prototype
- public card/object-page transition frames

### Core validation question

- does Community feel like public circulation of real MorpBase work instead of an adjacent content zone?

### Acceptance gate

- publish feels downstream from real work
- Discover feels useful
- import back into Memory feels like adoption into practice

## Slice 4. Continuity Activation

### Prototype artifacts

- medium-fidelity Continuity browse/select/appearance prototype
- transition prototype for Continuity -> Workspace activation

### Core validation question

- does Continuity feel meaningful, concrete, and correctly weighted?

### Acceptance gate

- entity meaning is clear
- appearances/recurrence are understandable
- activation visibly changes the Workspace context without bloating it

## Slice 5. Shell / Hierarchy Synthesis

### Prototype artifacts

- higher-fidelity stitched product flow across shell and main realms
- shell active-state and realm-switching behavior prototype

### Core validation question

- does the full product actually feel asymmetrical and coherent in lived use?

### Acceptance gate

- Workspace and Memory feel like the main lived product
- Community feels real but not default
- Continuity feels visible but lighter
- the shell feels calm, distinct, and product-shaped

## 4. Execution Sequence

### Phase A. Structural Center Pass

Build:

- Slice 1 low-fidelity flow
- Slice 1 medium-fidelity prototype

Purpose:

- validate the center before anything else gains weight

### Phase B. Center-To-Memory Pass

Build:

- Slice 2 Memory continuation prototype
- stitched Workspace -> Memory -> Workspace loop

Purpose:

- prove the second pole

### Phase C. Private-To-Public Pass

Build:

- Slice 3 publish/import/community loop

Purpose:

- validate Community through object circulation, not isolated browsing

### Phase D. Continuity Pass

Build:

- Slice 4 continuity activation prototype

Purpose:

- validate first-wave Continuity honestly and narrowly

### Phase E. Whole-Product Synthesis Pass

Build:

- Slice 5 shell/hierarchy stitched prototype

Purpose:

- confirm the total product feel and hierarchy

### Parallelization rule

Only light parallel work should happen.

What can overlap lightly:

- preparing visual/product direction references while medium-fidelity prototyping is underway
- preparing card/object display variants during Community work

What should stay sequential:

- center before Memory
- Memory before Community loop
- Continuity before final synthesis

## 5. Review And Gate Criteria

### Gate 1. Core Workspace Gate

Review:

- first-use clarity
- Prompt Preview trust
- keep/save meaning

Move on only if:

- first-use feels fast and real

Iterate if:

- the flow feels tutorial-like
- the workspace feels too dense or too form-like

### Gate 2. Memory Gate

Review:

- whether Memory feels active and essential
- whether branch/open/use are obviously central

Move on only if:

- Memory clearly feels like continuation

Iterate if:

- it still reads as archive/storage first

### Gate 3. Community Gate

Review:

- whether publish/import/public-object loops feel integrated

Move on only if:

- Community feels downstream from real work and upstream to reuse

Iterate if:

- it feels detached or decorative

### Gate 4. Continuity Gate

Review:

- whether Continuity is concrete enough
- whether activation has meaningful payoff

Move on only if:

- the realm feels real but not oversized

Iterate if:

- it feels abstract, too small to matter, or too heavy

### Gate 5. Whole-Product Synthesis Gate

Review:

- whole-product coherence
- shell hierarchy
- realm weighting

Prototype phase completes only if:

- the stitched experience still feels like one asymmetrical product

## 6. What Can Iterate vs What Must Stabilize

### Can Iterate During Prototype Phase

- detailed layout composition
- exact visual emphasis
- microcopy phrasing
- transition polish
- some card/public-surface presentation details

### Must Stabilize Before Moving On

- first-use Workspace logic
- Memory as second-pole behavior
- publish/import loop legitimacy
- Continuity activation meaning
- shell hierarchy feel

Rule:

- if a prototype slice still fails its core product role, later polish must not be used to mask it

## 7. End-State Of The Prototype Phase

At the end of the prototype phase, V2 should have:

- one validated first-use Workspace experience
- one validated Memory continuation loop
- one validated Community circulation loop
- one validated Continuity activation slice
- one validated stitched shell/hierarchy journey

And just as importantly:

- a clear list of what changed during prototyping
- a clear list of what remained stable
- a clear record of which blueprint assumptions survived contact with experience

## 8. Readiness For Implementation Planning

V2 should be considered ready for implementation planning only if:

1. first-use feels fast and strong
2. Memory clearly behaves as a second pole
3. Community feels integrated into object flow
4. Continuity feels meaningful but disciplined
5. shell hierarchy is felt clearly in lived use

If these are not true, implementation planning should wait and the relevant slice should iterate.

## 9. Final Judgment

The strongest execution workflow for the V2 prototype phase is:

- **a gated, sequential prototype program that proves the center first, the second pole second, the public loop third, continuity fourth, and the whole-product hierarchy last**

That is the cleanest way to test MorpBase V2 as a real experience before crossing the line into implementation planning.
