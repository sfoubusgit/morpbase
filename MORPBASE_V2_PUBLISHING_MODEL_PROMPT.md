# MorpBase V2 Publishing Model Prompt

You are analyzing **MorpBase V2** as a **completely new rebuilt product**, not as a refinement layered onto V1.

Your task is to determine the strongest **Publishing model** for the `Community` realm.

This is not a generic upload-dashboard exercise.

The Publishing surface must be analyzed inside the already-established V2 product structure:

- `Workspace` is the dominant center
- `Memory` is the strong second pole
- `Community` is a real public realm
- `Community` is structured around:
  - `Discover`
  - `Creators`
  - `Publishing`
- the public object model already has two primary object types:
  1. `Public Workflow Results`
  2. `Public Reusable Assets`
- public object pages and creator pages are already defined
- Discover is already defined as a layered object-circulation surface

Your job is to determine:

- what Publishing fundamentally should be
- how it should connect private MorpBase objects to public circulation
- how it should organize publication for the two public object types
- how much setup, management, and public-life control it should include
- how it should connect to Discover and creator pages
- how it should leave room for later challenge/event/public vitality without overbuilding first-wave

## Critical Constraints

- Treat V2 as a **fresh rebuild**
- Do **not** preserve V1 Pool Hub / upload logic by default
- Do **not** make Publishing just a generic upload page
- Do **not** make Publishing just a creator-settings page
- Do **not** make Publishing feel like a marketplace seller dashboard
- Do **not** detach Publishing from Memory
- Do **not** let Publishing become heavier than the actual creative center of the product

## Method

### 1. Start with real-life usage drafts first

Write at least 5 realistic publishing journeys such as:

- creator wants to publish a saved workflow result from Memory
- creator wants to publish a reusable asset for public reuse
- creator wants to see what is public vs private
- creator wants to improve a public object's presentation
- creator wants to update or withdraw a public object
- later event/challenge participation needs to attach to publishing without redefining it

For each draft, explain what structural demands it creates.

### 2. Generate multiple Publishing model candidates

Create at least 5 genuinely different Publishing models, such as:

- upload center
- public-settings manager
- creator studio
- circulation desk
- publish-from-memory-only with no real surface

You may create stronger alternatives if needed.

For each candidate, explain:

- what the surface fundamentally is
- what it emphasizes
- what it gets right
- where it fails

### 3. Compare the candidates seriously

Explicitly judge:

- clarity
- fit with Memory
- fit with the two-public-object model
- public usefulness
- management realism
- resistance to upload-dashboard drift
- resistance to marketplace drift
- support for public object quality
- support for later participation growth

### 4. Choose the strongest model or synthesis

Lock the best Publishing model for MorpBase V2.

### 5. Make the result concrete

Define:

- what Publishing fundamentally is
- the recommended page structure/order
- what is always visible
- what is lens-based
- how `Public Workflow Results` and `Public Reusable Assets` are handled
- how draft/ready/public states should appear conceptually
- what first-wave publication controls belong here
- what should stay for later

## Output Requirements

Write the result as:

`MORPBASE_V2_PUBLISHING_MODEL_ANALYSIS.md`

Structure it with:

1. Executive Conclusion
2. Real-Life Usage Drafts
3. Candidate Publishing Models
4. Comparison
5. Chosen Publishing Model
6. Recommended Page Structure
7. Relationship To Memory And Public Circulation
8. First-Wave vs Later Growth
9. Final Judgment

The final answer should be decisive, reflective, and product-structural.
