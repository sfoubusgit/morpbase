# Character Identity System Scope Boundary

## Purpose

If MorpBase ever introduces a reusable character system, the most important early question is:

- what belongs inside character identity
- and what must stay outside it

This boundary matters because the system will only be valuable if it remains:
- distinct from Pools
- distinct from Territories
- distinct from Modes
- distinct from the normal Builder workflow

## Core Rule

A Character Identity System should own:

- persistent subject identity

It should not own:

- full workflow styling
- scene construction
- territory focus
- final image-family definition

That is the core boundary.

## What Should Belong In Character Identity

### 1. Core identity anchors
These are the traits that make the character feel like the same character across multiple workflows.

Examples:
- archetype
- role
- age impression
- gender presentation
- general vibe

These are identity-level traits, not workflow-level traits.

### 2. Stable visual anchors
These are the recurring features that help preserve continuity.

Examples:
- hair identity
- face identity
- eye identity
- silhouette markers
- recurring clothing markers
- signature accessories

These are strong candidates for character ownership.

### 3. Recurring symbolic markers
A character may carry recurring motifs that are part of their identity rather than a specific workflow style.

Examples:
- crescent motif
- butterfly motif
- prayer charms
- mechanical insignia
- thorn ornament

These should belong in character identity only when they are truly part of the character across contexts.

### 4. Personality / emotional default
A character may have a general emotional flavor.

Examples:
- calm
- severe
- playful
- haunted
- noble

This should stay at the level of recurring character tone, not temporary scene mood.

### 5. Prompt-facing identity phrases
The system will likely need:
- concise reusable phrasing
- character-ready prompt fragments

These should express identity, not whole prompts.

## What Should Probably Stay Out

### 1. Style family
This belongs to Pools, not character identity.

Examples:
- pixel art
- painterly fantasy
- cinematic realism
- pastel sprite rendering
- ornate decorative sprite detailing

These define how the image looks, not who the character is.

### 2. Workflow identity
This belongs to Pools and Builder context.

Examples:
- `Celestial Pixel Portrait`
- `32x32 Pixel Art Portrait`
- future scene workflows

These are image-making lanes, not characters.

### 3. Territory focus
This belongs to Territories.

Examples:
- chosen source sections
- area bias
- current mapped builder categories

That is workflow focus, not character identity.

### 4. Scene-specific composition
This should generally stay out of character identity.

Examples:
- centered bust portrait
- low-angle action shot
- wide environmental framing
- profile silhouette shot

These are image decisions.

At most, a character might have weak recurring preferences, but composition should not become a core character field.

### 5. Temporary scene mood
This should mostly stay outside.

Examples:
- battle tension
- eerie moonlit stillness
- celebratory warmth
- stage-performance energy

These are often context-specific, not identity-specific.

### 6. Broad prompt polish layers
These belong elsewhere.

Examples:
- masterpiece
- sharp focus
- atmospheric depth
- rich textures

Those are not character identity.

## Borderline Areas

Some areas are not purely inside or outside.

These need careful handling.

### Clothing
Clothing may belong in character identity when it is:
- iconic
- recurring
- part of the recognizable character silhouette

Clothing should stay outside character identity when it is:
- style- or scene-specific
- one-off
- primarily determined by the workflow

### Accessories
Accessories can belong in character identity if they are:
- signature
- recurring
- strongly identity-linked

But generic accessory language should stay in Pools or secondary Pools.

### Motifs
Motifs belong in character identity only if they are:
- persistently attached to the character

If they are mostly a style family pattern, they belong to the host workflow instead.

### Personality
Personality belongs when it is:
- a persistent identity trait

But temporary emotional performance belongs to the specific prompt/workflow.

## Best Ownership Model

### Character Identity owns:
- who the character is
- what recurring visual/identity anchors define them

### Pools own:
- how the character appears inside a style/workflow family

### Territories own:
- source-space focus and contextual shaping

### Builder owns:
- current step-by-step prompt construction

### Global Phrase Layer owns:
- user-level persistent generic prompt modifiers

This division is clean and worth protecting.

## What A Good Character Identity Output Should Feel Like

It should feel like:
- a reusable subject identity profile

It should not feel like:
- a complete image prompt
- a workflow baseline set
- a territory
- a style package

That distinction is essential.

## A Practical Litmus Test

Ask:

- "Could this trait remain true if I moved the character into a very different pool?"

If yes:
- it probably belongs in character identity

If no:
- it probably belongs elsewhere

Examples:

### Belongs
- black-to-silver gradient hair
- solemn gaze
- crescent charm earrings
- ritual priestess archetype

### Does not belong
- luminous anime pixel portrait
- centered symmetrical bust framing
- ornate decorative sprite detailing
- starry dark background

## Why This Boundary Matters

Without this boundary:
- pools and characters will overlap
- prompts will become harder to reason about
- system clarity will drop
- MorpBase will add complexity without real new leverage

With this boundary:
- characters can become truly reusable
- pools can stay workflow/style-focused
- the product remains legible

## Honest Conclusion

The Character Identity System should be narrow in a very specific way:

- broad across workflows
- narrow in what it owns

It should own:
- recurring subject identity

It should not own:
- final stylistic realization
- scene construction
- workflow specialization

That is what gives the idea a chance of being genuinely valuable instead of redundant.
