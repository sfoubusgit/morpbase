# Identity Systems Realm Placement

## 1. Executive Conclusion

`Identity Systems` should be treated as a **future major MorpBase realm**, but not yet as a **live top-level product center**.

The cleanest current placement is:

- **conceptually major**
- **structurally separate from Builder**
- **parallel to Workflow Sources, not inside it**
- **upstream of Prompt Archive**
- **outside Pool Hub and Profiles**
- **product-visible later, not now**

So the strongest present-tense judgment is:

- `Identity Systems` is a **latent future major realm**

That means:

- it already deserves realm-level conceptual treatment
- it does not yet deserve equal live-product visibility beside Builder in the current app shell

This is the healthiest balance because:

- Builder remains the center of use
- Identity keeps its dignity as a distinct future realm
- the product avoids overcommitting before the first proving lane and archive-grounded evidence exist

---

## 2. Recommended Realm Placement

The recommended placement is:

- **outside the Builder workspace**
- **outside Workflow Sources**
- **adjacent to other support realms conceptually**
- **not yet exposed as a live primary navigation destination**

The cleanest structural reading is:

### Core center

- Builder + Prompt Preview

### Support realms

- Workflow Sources
- Identity Systems
- Prompt Archive

### Ecosystem layer

- Pool Hub
- Profiles / creator surfaces

Under this reading:

- Workflow Sources owns reusable source material and Territory authoring
- Identity Systems owns reusable continuity entities
- Prompt Archive owns saved outputs and reuse of results

That means Identity belongs:

- nearer to Builder than Pool Hub does
- nearer to Workflow Sources than Prompt Archive in conceptual role
- but not nested under Workflow Sources

The most precise product-structure label for now is:

- **latent major support realm**

not:

- minor advanced feature
- hidden implementation detail
- already-live top-level realm

---

## 3. Navigation-Level Judgment

### Does Identity Systems conceptually deserve dedicated top-level navigation?

Yes.

The concept is large enough and structurally distinct enough that it eventually justifies its own navigation realm.

Why:

- it is not just a sub-feature of Builder
- it is not just another part of Workflow Sources
- it is not downstream archive structure
- it can plausibly become one of MorpBase's strongest long-term support domains

### Should it be visible as a live top-level navigation realm now?

No.

Not yet.

Why:

- the first proving lane is not settled in live product reality
- the concept is not yet validated strongly enough through repeated use
- the current runtime still reflects premature Character-shaped drift
- a visible live realm would imply more commitment than the product has earned yet

### Best current navigation judgment

- conceptually: **yes, realm-worthy**
- product-right-now: **no, not yet top-level live navigation**

### Best classification right now

- **latent future major realm**

This is more accurate than:

- `advanced feature`
- `minor support tool`

and safer than:

- `already-live first-class navigation realm`

## 4. Relationship To Existing Top-Level Surfaces

### Builder

Identity Systems should not challenge Builder as the primary center of use.

Correct relationship:

- Builder remains where the live workflow is authored
- Identity remains a separate realm that feeds into Builder sessions

So Identity should sit:

- beside Builder conceptually
- but not as an equal center of active use

### Workflow Sources

This is the closest neighboring realm.

Correct relationship:

- Workflow Sources = Pools + Territories + source-space authoring
- Identity Systems = reusable continuity entities

This makes them:

- conceptual neighbors
- but not parent/child

Identity should not be placed under Workflow Sources because that would imply:

- identities are another kind of source material

which is exactly the wrong mental model.

### Prompt Archive

Prompt Archive is downstream from Builder.
Identity Systems is upstream support for recurring continuity.

Correct relationship:

- Identity helps shape repeated outputs
- Prompt Archive stores the outputs created with or around those identities

So Prompt Archive should remain:

- downstream of Identity in product meaning

not:

- the parent of Identity

### Pool Hub

Pool Hub is ecosystem and discovery for Pools.

Identity Systems should not be placed under Pool Hub because that would imply:

- identity is another community content library of the same basic kind

That is too Pool-shaped and weakens the realm.

Correct relationship:

- separate ecosystem domain later, if identity publishing ever exists

### Profiles

Profiles are creator / authorship surfaces.

Identity should not be placed under Profile because that would imply:

- identity entities are profile assets first

That is also the wrong hierarchy.

Correct relationship:

- profiles may later reference published identities
- but Identity Systems remains its own domain

### Current App Shell Reading

The current shell in `src/ui/App.tsx` already groups:

- Builder as `Main Workspace`
- Saved Prompts / Workflow Sources / Community Pools / Profile as `Support Tools`

That shell does not currently have an Identity realm surface, and this is actually appropriate for the current stage.

What should change later is not:

- forcing Identity into one of the existing surfaces

but:

- making room for it as its own support-realm surface once it has earned that status

## 5. Why This Placement Fits MorpBase

### 1. It respects Builder-centered product truth

`MORPBASE_PRIMARY_USER_FACING_CENTER_DECISION.md` already locked:

- Builder + Prompt Preview loop is the center of use

This placement keeps that intact.

### 2. It preserves the entity boundary

A separate realm placement prevents identity from being misread as:

- another Pool shape
- another Territory mode
- another Builder content lane

### 3. It matches the selected direction

The direction selection already locked:

- main direction = Continuity Realm Model
- grounding constraint = Archive Lineage Model
- horizon = Continuity Universe Model

That combination implies:

- Identity must be big enough to be a realm
- but not yet visible enough to overclaim product maturity

### 4. It keeps future growth possible

If the first proving lane succeeds, this placement leaves room for:

- Character Identity
- Outfit / Clothing Identity
- later additional lanes

without requiring a total product reframe.

### 5. It avoids premature product inflation

A visible top-level realm now would make Identity feel more settled than it really is.

This placement avoids that.

## 6. What Would Be Premature

### 1. Adding a live top-level `Identity Systems` nav button now

This would overstate product maturity.

### 2. Nesting Identity under Workflow Sources

That would wrongly teach:

- identity = another kind of source material

### 3. Framing Identity as part of Prompt Archive

That would wrongly teach:

- identity = saved-output organization or lineage only

### 4. Framing Identity as part of Profile

That would wrongly teach:

- identity = creator-profile asset first

### 5. Treating the current Character prototype as proof of full realm readiness

The current runtime is useful pressure-test material, but it does not justify full placement commitment yet.

### 6. Letting the continuity-universe horizon shape current placement

The larger future continuity vision should remain latent, not drive present product structure.

## 7. What Must Be True Before Realm Visibility Expands

### 1. The first proving lane must be clearer

MorpBase needs a more settled answer on:

- Character only
- Character with realm preserved
- or some slightly broader first visible shape

### 2. Real repeated-use evidence must exist

This is the archive-lineage grounding rule.

Identity should earn greater visibility through evidence that:

- continuity is being used repeatedly
- the gap is real
- the system is not just elegant in theory

### 3. The current Character runtime drift must be interpreted correctly

Before visibility expands, MorpBase must be clear whether current Character code is:

- disposable scaffolding
- or intentional prototype pressure-test material

### 4. The relationship to Workflow Sources must be legible

Users must be able to understand:

- Workflow Sources = source material and Territory authoring
- Identity = reusable continuity entities

without collapse.

### 5. Prompt-layer legibility must improve enough

If users cannot tell the difference between:

- active Territory
- active source Pools
- active IDP baseline
- active identity

then expanding realm visibility will make the product heavier too early.

### 6. The first user-facing label may need to be softer than the architecture label

Before a visible top-level realm appears, MorpBase may need to decide whether:

- `Identity Systems`

is the live label,

or whether:

- the realm concept stays internal while the first visible lane uses a narrower label like `Characters`

This question does not block concept work, but it does block clean product exposure.
