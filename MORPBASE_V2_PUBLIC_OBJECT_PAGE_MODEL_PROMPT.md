# MorpBase V2 Public Object Page Model Prompt

You are designing the page model for the two primary public object types in MorpBase V2.

This is a whole-product V2 decision for a fresh rebuild in a new project folder.
This is not visual design yet.
This is structural page logic.

The two already chosen primary public object types are:

1. `Public Workflow Results`
2. `Public Reusable Assets`

Your job is to determine:

- what a strong public object page must contain
- what page grammar should be shared between both object types
- what must differ between them
- how import, creator grounding, utility, and workflow relevance should appear

## Already Locked

Respect these truths:

- Workspace is the dominant center
- Memory is the strong second pole
- Community is built around:
  - Discover
  - Creators
  - Publishing
- public object pages must become serious product surfaces
- creator pages should be object-grounded
- imports from Community land in Memory
- MorpBase should learn from CivitAI-style object page strength without copying CivitAI directly
- first-wave public object model has only two primary object types:
  - Public Workflow Results
  - Public Reusable Assets

## Working Rule

Use this method:

1. make real-life usage drafts first
2. compare multiple page models
3. then choose what works best, or combine

## Main Goal

Determine:

- the shared page grammar both object types should use
- the structural differences between the two object pages
- what sections are mandatory
- what actions matter most
- how each page communicates:
  - what this is
  - why it is useful
  - who made it
  - why it is worth importing, branching from, or following

## Real-Life Usage Drafts First

Before choosing the page model, create at least 5 realistic usage drafts:

1. user lands on a public workflow result page from Discover
2. user lands on a public reusable asset page from Discover
3. user reaches an object page from a creator page
4. user decides whether to import or follow from the page
5. creator checks how their published object represents them publicly

## Candidate Page Models To Compare

Compare at least:

- metadata-first page model
- creator-story-first page model
- utility/action-first page model
- balanced shared grammar model
- any hybrid that emerges from the drafts

## Questions You Must Answer

1. What page grammar should both public object types share?
2. What sections must every strong public object page contain?
3. What actions should be primary on each page?
4. What makes a Public Workflow Result page structurally different from a Public Reusable Asset page?
5. How should creator grounding appear?
6. How should import / branch / use actions differ by object type?
7. What should remain metadata, and what should be elevated into major page sections?
8. How should later continuity-linked enrichment appear without redefining the page model?

## Hard Constraints

Do not let the page model become:

- thin metadata sheets
- CivitAI clones
- blog-post-like object pages
- giant control panels
- creator pages in disguise

## Output Requirements

Write the result to:

- `MORPBASE_V2_PUBLIC_OBJECT_PAGE_MODEL_ANALYSIS.md`

Include:

- executive conclusion
- real-life usage drafts
- candidate page models
- comparison
- chosen shared page grammar
- shared required sections
- object-type-specific differences
- primary action decisions
- creator grounding decision
- continuity-enrichment treatment
- strongest risks
- final recommendation

Be decisive, but question your assumptions before locking the result.
