# MorpBase V2 New Project Build Brief

## 1. Executive Conclusion

The new V2 project should start as:

- **a fresh MorpBase rebuild centered on the real `Workspace + Memory` loop**

This project should not begin as:

- a port of V1
- a partial prototype in code
- or a broad platform build

It should begin as:

- the first real coded version of MorpBase V2's heart

That means the project starts by proving:

- live creation
- meaningful keep
- living memory
- natural return into creation

## 2. Project Purpose

The purpose of the new V2 project is:

- to turn the proven V2 product truth into a real new codebase

More plainly:

- build the new MorpBase from the center outward
- keep the product strong, simple, and integrated
- and avoid the V1 mistake of growing many systems before the core product is fully coherent

The project should be treated as:

- the beginning of the real product

not:

- an experiment
- a redesign overlay
- or a technical migration shell

## 3. Slice 1 Inside The Project

The first build slice inside the new project is:

- **the real `Workspace + Memory` core loop**

That means the project starts with:

- `Workspace`
- `Prompt Preview`
- `Keep`
- `Memory Home`
- one kept-work focus
- and return to `Workspace`

This is the first slice because it is the smallest version of V2 that can already feel like MorpBase.

## 4. What Is Included From The Start

The new project should include these things from the start:

### Must include

- the asymmetric V2 shell
- `Workspace` as the dominant center
- persistent `Prompt Preview`
- the guided live creation flow
- a meaningful `Keep` moment
- `Memory Home`
- one real kept-work path
- reopen / branch / continue return behavior
- proof-image support where needed
- frozen V2 naming
- anti-generic design discipline

These are the minimum pieces needed for the project to feel like the beginning of the real V2 product.

## 5. What Is Excluded From The Start

The new project should explicitly keep these out at the start:

### Must exclude

- `Community`
- `Continuity`
- public publishing
- import flows
- collaboration systems
- challenge systems
- reward systems
- storyline systems
- advanced creator/profile depth
- deeper reusable-asset systems
- V1 carryover structures that are not needed for Slice 1

These are important later, but they should not be part of the project start scope.

## 6. First Coding Checkpoint

The first coding checkpoint should ask one simple question:

- **does the new project already feel like real MorpBase in its first loop?**

More concretely, the checkpoint passes only if:

- `Workspace` feels like the real center
- `Prompt Preview` builds trust
- `Keep` feels earned
- `Memory` feels like a second home, not storage
- return into `Workspace` feels like continuation, not reset

If these things are not true, the project is not ready to widen.

## 7. Project-Start Guardrails

These guardrails should stay active from day one:

### 1. No V1 carryover by convenience

### 2. No broad platform thinking in Slice 1

### 3. No generic AI/SaaS shell drift

### 4. No image-first drift

### 5. No storage-like Memory behavior

### 6. No early `Community` or `Continuity` leakage

### 7. No over-modeling before the core loop feels alive

## 8. Why This Project Start Is Strongest

This project start is strongest because it begins exactly where MorpBase is now clearest:

- the live center
- the second home
- and the return loop between them

It gives the new codebase a chance to become:

- coherent early
- product-real early
- and distinct early

instead of:

- broad early
- messy early
- or generic early

## 9. Final Next-Step Recommendation

The next artifact after this build brief should be:

- **the new V2 project start checklist**

That should turn this brief into a simple startup action list:

- folder/project creation
- active control docs
- Slice 1 starting scope
- first implementation focus
- first checkpoint target

## 10. Final Judgment

`The new MorpBase V2 project should begin as a fresh codebase whose first real job is to prove the `Workspace + Memory` core loop as a living product experience, while explicitly holding back broader platform systems until the heart of V2 is alive in code.`
