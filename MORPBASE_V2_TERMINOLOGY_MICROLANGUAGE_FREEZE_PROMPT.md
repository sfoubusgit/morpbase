# MorpBase V2 Terminology And Micro-Language Freeze Prompt

You are analyzing **MorpBase V2** as a **completely new rebuilt product in a new project folder**, not as a refinement of V1.

Your task is to create the **Terminology And Micro-Language Freeze** for V2 first-wave.

This phase comes **after**:

- foundation freeze
- product blueprint
- interaction blueprint

It is the final language-consolidation phase before design-universe preparation and experience prototyping.

This is **not** a broad naming-philosophy exercise anymore.
The naming philosophy is already established.

Now the job is to freeze:

- what users will actually read
- what key surfaces are called
- what repeated object names are
- what the main action verbs are
- how the product should sound consistently

## Core Context

The governing documents now are:

- `MORPBASE_V2_FOUNDATION_FREEZE.md`
- `MORPBASE_V2_PRODUCT_BLUEPRINT.md`
- `MORPBASE_V2_INTERACTION_BLUEPRINT.md`
- `MORPBASE_V2_NAMING_TERMINOLOGY_ANALYSIS.md`

You must treat those as constraints.

Already near-frozen:

- top-level realm names:
  - `Workspace`
  - `Memory`
  - `Community`
  - `Continuity`
  - `Profile`

What is not fully frozen yet:

- sub-surface names
- repeated object labels
- key action/verb language
- first-use and transition language
- what stays backstage vs front-stage

## What This Freeze Must Cover

At minimum, freeze:

### 1. Realm and section names

- final first-wave user-facing names for major sections

### 2. Repeated object names

- what saved things are called
- what reusable things are called
- what public things are called
- what continuity things are called

### 3. Action language

- save/keep language
- branch/reopen/use language
- publish/import language
- continuity activation language

### 4. First-use language

- how the product sounds during the guided first-flow
- how guidance feels helpful without sounding tutorial-heavy or robotic

### 5. Product tone rules

- what the language should feel like overall
- what it must avoid

### 6. Backstage discipline

- what architecture words stay internal
- what should not leak back into front-stage V2 language

## Critical Constraints

- Treat V2 as a **fresh rebuild**
- Obey the existing freeze/blueprint/interaction docs
- Do **not** reopen broad product-structure questions
- Do **not** let language become generic SaaS mush
- Do **not** reintroduce V1 jargon through “helpful” terminology
- Do **not** make microcopy over-clever, over-poetic, or lore-heavy

## Method

### 1. Start with real-life language-use drafts first

Write at least 5 realistic language moments such as:

- first-time user sees the shell and the first-use workspace guidance
- user reaches the keep/save moment
- user uses Memory to reopen or branch work
- creator publishes something into Community
- user activates continuity in Workspace

For each moment, explain what language demands it creates.

### 2. Re-state the existing naming system in practical terms

Translate the naming philosophy into actual product-language needs.

### 3. Freeze language by category

For each category, provide the recommended first-wave terms:

- realm names
- section names
- object names
- action verbs
- transition language

### 4. Define tone and consistency rules

State how V2 should sound:

- concise vs expressive
- instructional vs invitational
- product-real vs conceptual

### 5. Define banned / retired language

Be explicit about which V1 and analysis-layer terms should not surface in front-stage product language.

### 6. End with readiness judgment

State whether the terminology system is now strong enough to move into:

- design-universe preparation
- and then experience prototyping

## Output Requirements

Write the result as:

`MORPBASE_V2_TERMINOLOGY_MICROLANGUAGE_FREEZE.md`

Structure it with:

1. Executive Conclusion
2. Real-Life Language-Use Drafts
3. Practical Naming System Restated
4. Frozen Realm And Section Names
5. Frozen Object Names
6. Frozen Action And Transition Language
7. Tone And Consistency Rules
8. Backstage / Retired Language
9. Readiness For Design-Universe Preparation
10. Final Judgment

The result should be decisive, product-facing, and strong enough to serve as the governing language reference before visual-system work begins.
