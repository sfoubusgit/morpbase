# MorpBase V2 Master Reassessment And Build Workflow Prompt

You are analyzing **MorpBase V2** as a **completely new rebuilt product in a new project folder**, not as a refinement of V1.

Your task is to perform a **master reassessment** of everything established so far about V2, and then produce a **reconsolidated workflow for actually creating V2**.

This is not a local realm prompt.
This is not a new feature prompt.
This is a meta-level reset and consolidation pass.

You must challenge the current V2 direction honestly and decide:

- what still holds
- what is still only provisional
- what may be overbuilt or over-theorized
- what the strongest current product truth actually is
- and what the correct workflow for building V2 should now be from this point forward

## Core Context

V2 is meant to be:

- a true successor to V1
- not a smaller side-product
- not a compromise version of MorpBase
- a complete rebuild in a new codebase

The non-negotiable principle is:

- preserve the **heart** of MorpBase
- but allow radical change to terminology, structure, surfaces, and systems if that produces a stronger product

Important strategic warnings already established:

- V1 suffered from continuous feature addition without enough big-picture discipline
- V2 must not repeat that
- not every conceptual realm should automatically become a first-wave product center
- not every user-facing name should be preserved from V1
- the product should become more user-friendly, stronger, clearer, and more competitive than wildcard / dynamic-prompt style alternatives
- the design should eventually live inside a **real custom visual universe**, not a generic app skin

Important working preference:

- think through real-life usage drafts first
- then compare alternatives
- then choose or synthesize

## Method

### 1. Start with real-life whole-product usage drafts first

Write at least 5 realistic whole-product journeys that pressure-test the current V2 picture.

Examples:

- first-time user enters V2, creates something meaningful, keeps it, and returns later
- user moves between Workspace and Memory repeatedly and feels whether the product center is really strong
- creator engages with Community from real work and back into private use
- continuity-aware user uses recurring entities without the product feeling abstract or overbuilt
- advanced user touches multiple layers and tests whether the product still feels like one product

For each draft, explain what these journeys demand from the total V2 structure.

### 2. Re-state the current V2 picture as one product

Summarize the current V2 direction as one coherent system.
Do not just list the docs.

### 3. Reassess every major layer

For each major layer, judge whether it is:

- solid
- directionally right but still provisional
- too early
- too heavy
- too abstract
- or in need of correction

You should explicitly reassess:

- center / workspace
- memory
- continuity
- community
- shell
- first-use
- naming

### 4. Identify the biggest current risks

Look for things like:

- equal-center drift
- concept inflation
- too much architecture-thinking vs product-thinking
- first-wave over-scope
- weak transition model
- weak product distinctiveness
- design identity being under-accounted for
- continuity being either too vague or too staged

### 5. Compare at least 3 whole-direction readings

For example:

- current V2 direction mostly holds
- current V2 direction needs selective simplification and sharper workflow
- current V2 direction is still too broad and needs stronger narrowing before build

You may define better alternatives if needed.

### 6. Choose the strongest final reading

Decide:

- what definitely holds
- what should be revised
- what should be frozen
- what should be deferred

### 7. Reconsolidate the actual workflow of creating V2

This is essential.

Produce a **real build workflow** from here onward, not just more conceptual layers.

Define:

- what must be frozen before design starts
- what must be designed before code starts
- what can remain flexible
- what sequence the V2 creation process should follow now
- what should happen in Phase 1, Phase 2, Phase 3, etc.

This workflow should cover at least:

- product foundation freeze
- product blueprint / information architecture
- interaction blueprint
- naming freeze
- design-universe / visual-system preparation
- prototype / validation layer
- implementation planning
- actual new-project build start

### 8. End with a strict decision

State clearly:

- whether V2 is ready to move into blueprint/design mode
- whether more product-level clarification is still required first
- and what the single best next step is
