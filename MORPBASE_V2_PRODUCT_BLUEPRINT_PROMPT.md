# MorpBase V2 Product Blueprint Prompt

You are analyzing **MorpBase V2** as a **completely new rebuilt product in a new project folder**, not as a refinement of V1.

Your task is to create the **Product Blueprint** for V2 first-wave.

This is the phase that comes **after** the foundation freeze.

It is no longer acceptable to keep expanding the product concept map broadly.
The goal now is to translate the frozen V2 foundation into a **concrete, navigable, screen-level product blueprint**.

## Core Context

The V2 foundation is already frozen in:

- `MORPBASE_V2_FOUNDATION_FREEZE.md`

You must treat that document as the governing constraint.

The most important frozen truths are:

- V2 is a new product build
- preserve the heart, not the old nouns
- `Workspace` is the unmistakable center
- `Memory` is the indispensable second pole
- `Continuity` is a real but lighter support realm
- `Community` is a real but downstream public circulation layer
- `Profile` is utility-level
- first-use is direct-to-workspace with a guided first-flow layer
- the product hierarchy must remain asymmetrical

## What The Product Blueprint Must Do

The blueprint must answer:

- what the actual first-wave product screens are
- what each major screen family contains
- how users move between them
- what object flows connect them
- what is top-level vs contextual vs backgrounded
- how the product remains one product rather than a cluster of realms

This is **not yet** a visual design system task.
This is **not yet** implementation planning.
This is the screen and structure blueprint that later UX, design, and engineering can build on.

## What To Blueprint

At minimum, the blueprint must cover:

### 1. Workspace blueprint

- the main workspace shell
- guided authoring area
- Prompt Preview area
- save/keep pathways
- where support/context systems enter

### 2. Memory blueprint

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`
- how imported public objects land inside Memory

### 3. Continuity blueprint

- `Continuity Home`
- `Entities`
- `Appearances` / continuity-through-work
- how Continuity activates into Workspace

### 4. Community blueprint

- `Discover`
- `Creators`
- `Publishing`
- public object flow
- import/publish relationships

### 5. Shell and transition blueprint

- what the shell reveals at all times
- what transitions are primary
- what transitions are contextual
- how asymmetry is expressed through real product structure

### 6. First-use blueprint

- what the first-use workspace state looks like structurally
- what is shown / dimmed / hidden
- how the user reaches first success
- how Memory becomes meaningful after that

## Critical Constraints

- Treat V2 as a **fresh rebuild**
- Obey the foundation freeze
- Do **not** reopen broad foundation questions unless something clearly breaks under blueprint pressure
- Do **not** flatten the product into equal pages
- Do **not** overbuild visual solutions before structural blueprinting is done
- Do **not** let blueprinting drift into implementation details

## Method

### 1. Start with real-life blueprint journeys first

Write at least 5 realistic product journeys that require screen-level structure, such as:

- first-time user enters Workspace, creates, and keeps a result
- returning user branches from Memory into Workspace
- user activates a continuity entity into a live workflow
- creator publishes from Memory into Community
- user discovers something in Community and imports it back into Memory

For each journey, explain what screen-level structure and transitions it demands.

### 2. Re-state the frozen V2 product in blueprint terms

Summarize the frozen foundation as a product blueprint problem.

### 3. Define the major screen families

For each major screen family, define:

- purpose
- primary objects
- major sections
- key entry paths
- key outgoing transitions

### 4. Define the cross-product object flow

Explain how the main product objects move across screens:

- active workflow session
- saved work
- reusable assets
- continuity entities
- public workflow results
- public reusable assets

### 5. Define top-level vs contextual access

Be explicit about:

- what is entered directly from shell
- what is entered contextually from another screen
- what is background/supportive rather than front-stage

### 6. Identify blueprint risks

Look for:

- screen inflation
- duplicated surfaces
- weak realm transitions
- abstract realms with weak screen value
- hidden equal-center drift

### 7. End with the blueprint outcome

The final result should say:

- whether the V2 product blueprint is now strong enough to proceed into interaction blueprint work
- and what the next step should be

## Output Requirements

Write the result as:

`MORPBASE_V2_PRODUCT_BLUEPRINT.md`

Structure it with:

1. Executive Conclusion
2. Real-Life Blueprint Journeys
3. Frozen Foundation Restated For Blueprinting
4. Major Screen Families
5. Cross-Product Object Flow
6. Top-Level vs Contextual Access
7. Primary Transitions
8. Blueprint Risks
9. Readiness For Interaction Blueprint
10. Final Judgment

The result should be decisive, screen-structural, and strong enough to become the governing V2 product blueprint before interaction design begins.
