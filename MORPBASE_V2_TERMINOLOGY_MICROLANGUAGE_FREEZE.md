# MorpBase V2 Terminology And Micro-Language Freeze

## 1. Executive Conclusion

The strongest first-wave terminology system for MorpBase V2 is:

- **clear realm language, concrete object language, calm action language, and strict backstage discipline**

This means V2 should sound:

- product-real
- concise
- invitational
- and structurally clear

It should not sound:

- overnamed
- overexplained
- tutorial-heavy
- generic-SaaS bland
- or burdened by V1 internal jargon

The main language law is:

- **users should understand what they can do and what things are for without needing the product to explain its internal architecture**

So this freeze locks:

- the main user-facing realm and section names
- the repeated object labels
- the core action verbs
- the product tone rules
- and the terms that must stay backstage

## 2. Real-Life Language-Use Drafts

### Draft 1. First-time user sees the shell and the first-use workspace guidance

Goal:

- understand where they are
- know what to do first
- not feel talked down to

What this demands:

- realm names must scan fast
- first-use language must guide without sounding like a tutorial voiceover
- the product should sound confident and calm, not explanatory by default

### Draft 2. User reaches the keep/save moment

Goal:

- feel they made something worth preserving

What this demands:

- the keep/save language must feel meaningful
- not like generic file storage
- and not like an internal “archive action”

### Draft 3. User uses Memory to reopen or branch work

Goal:

- understand that Memory is active continuation, not storage

What this demands:

- action verbs must emphasize continuation:
  - `Open`
  - `Branch`
  - `Use`
- and avoid making Memory sound like a file cabinet

### Draft 4. Creator publishes something into Community

Goal:

- feel that they are giving real work a public life

What this demands:

- `Publish` must sound serious but simple
- the object names in Community must feel useful and credible
- Community language must avoid feed/platform slang

### Draft 5. User activates continuity in Workspace

Goal:

- understand that recurring sameness has been brought into the current session

What this demands:

- continuity language must be concrete at the action level
- `Activate` / `Use in Workspace` style verbs are clearer than abstract continuity phrasing

These moments strongly suggest:

- the language should carry function first
- identity second
- and internal system theory not at all

## 3. Practical Naming System Restated

The naming system now translates into these practical rules:

### 1. Top-level names must be immediately legible

Users should understand the shell without product-specific study.

### 2. Repeated objects must be concrete

Users should quickly understand what an object is for.

### 3. Repeated actions must be short and strong

The product should use stable verbs that imply movement and continuity.

### 4. Distinctiveness should come from structure and later design universe

Not from a large volume of unusual product nouns.

### 5. Internal architecture language stays internal

If a term mainly serves analysis, architecture, or product strategy, it should not become front-stage language automatically.

## 4. Frozen Realm And Section Names

### Top-level realm names

These are now frozen for first-wave:

- `Workspace`
- `Memory`
- `Community`
- `Continuity`
- `Profile`

### Workspace

Keep:

- `Workspace`
- `Prompt Preview`

Likely first-wave internal section labels:

- `Prompt Preview`
- `Keep` / `Save`

Do not force extra branded labels here.

### Memory

Freeze:

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`

These work because they make `Memory` concrete immediately.

### Community

Freeze:

- `Discover`
- `Creators`
- `Publishing`

These are clear intention-based names and should stay.

### Continuity

Freeze:

- `Continuity Home`
- `Entities`
- `Appearances`

Note:

- `Appearances` is the stronger user-facing term than `Lineage` in first-wave.
- `Lineage` can remain explanatory/backstage where needed.

### Profile

Keep:

- `Profile`

Do not expand this into more product-like naming.

## 5. Frozen Object Names

### Workspace / Memory objects

Freeze these first-wave object labels:

- `Saved Work`
- `Reusable Assets`
- `Capture`

Why:

- these are concrete
- they map cleanly to user intention
- and they keep `Memory` understandable

### Community public object labels

For front-stage user-facing language, freeze:

- `Published Work`
- `Reusable Assets`

For backstage / structural language, allow:

- `Public Workflow Results`
- `Public Reusable Assets`

Rule:

- use the simpler pair in repeated product-facing surfaces
- keep the heavier pair for strategy/spec references only when needed

### Continuity objects

Freeze for first-wave:

- `Characters`

Allow as later lane names, not first-wave promises:

- `Outfits`
- `Artifacts`
- `Creatures`

### Creator/public identity

Freeze:

- `Creator`

Avoid:

- influencer-like or platform-social alternatives

## 6. Frozen Action And Transition Language

### Core creation / preservation verbs

Freeze:

- `Keep`
- `Save`
- `Open`
- `Use`
- `Branch`

Behavior guidance:

- `Keep` is strongest when the product is asking “is this worth preserving?”
- `Save` is strongest in more explicit record/persistence moments
- both can coexist if used intentionally

### Community verbs

Freeze:

- `Publish`
- `Import`
- `Follow`

Why:

- short
- clear
- credible
- product-real

### Continuity verbs

Freeze:

- `Activate`
- `Use in Workspace`

Allow:

- `View Appearances`

Avoid:

- overly abstract verbs like “bind,” “project,” or “instantiate”

### Transition language

The product should consistently imply these transition meanings:

- `Workspace -> Memory` = `Keep` / `Save`
- `Memory -> Workspace` = `Open`, `Branch`, `Use`
- `Memory -> Community` = `Publish`
- `Community -> Memory` = `Import`
- `Continuity -> Workspace` = `Activate`

These verbs should stay stable across the product.

## 7. Tone And Consistency Rules

### Tone

V2 should sound:

- concise
- calm
- inviting
- product-real

It should not sound:

- overly cheerful
- robotic
- lore-heavy
- over-poetic
- tutorial-heavy

### Instruction style

Prefer:

- short directional language
- action-first wording
- guidance that feels like narrowing attention, not teaching a course

### Product voice

The product should sound like:

- a serious creative tool
- not a playground
- not an enterprise dashboard
- not a mystical system

### Consistency rule

If a shorter clearer word exists and does not reduce meaning too much, prefer it.

If a more expressive word adds identity but increases explanation cost, reject it unless it solves a real product problem.

## 8. Backstage / Retired Language

### Backstage / internal-only language

These should remain mostly backstage:

- `active workflow session`
- `workflow-shaping assets`
- `continuity entities`
- `lineage semantics`
- `shared creative objects`
- other architecture/spec phrases of that kind

### Retired V1 front-stage terms

These should not return as first-wave user-facing language:

- `Working Sets`
- `Pools`
- `Territories`
- `IDP Sets`
- `Initiative Phrases`
- `Prompt Sets` as a major front-stage noun

Important nuance:

- some underlying functions may survive
- but these terms are not part of the front-stage V2 language system

### Language to avoid generally

- over-clever coined verbs
- platform-social slang
- market/listing jargon
- abstract system labels that require documentation to decode

## 9. Readiness For Design-Universe Preparation

The terminology and micro-language system is now strong enough to move into:

- **design-universe preparation**

And after that:

- **experience prototyping**

Why:

- top-level language is frozen
- repeated object and action language is now stable enough
- tone and backstage discipline are explicit
- the later design phase can now build identity around a stable language layer instead of compensating for unstable terminology

## 10. Final Judgment

The strongest first-wave language system for MorpBase V2 is:

- **a clear, calm, product-real language system with stable realm names, concrete repeated object labels, short action verbs, and strict backstage discipline**

That is now strong enough to stop naming drift and hand V2 into design-universe preparation with a stable product voice.
