# MorpBase V2 Memory Structure Analysis

## 1. Executive Conclusion

The strongest internal structure for `Memory` in MorpBase V2 is:

- **a living memory hub with two core object pillars, one capture inbox, and one recent-flow landing view**

More concretely:

- `Memory Home` as the default landing view
- `Saved Work` as the first major object pillar
- `Reusable Assets` as the second major object pillar
- `Capture Inbox` as the lightweight rough-memory lane

And then:

- imported public objects should land inside the appropriate pillar, not in a separate imported realm
- continuity-linked traces should appear as metadata, badges, and filters, not as a primary first-wave Memory section

This is the best result because it avoids both bad extremes:

- Memory as a passive archive cabinet
- Memory as a broad library that collapses unlike things into one vague zone

The key judgment is:

- `Memory needs both object clarity and flow clarity`

So the right answer is not just "archive" or "library."
It is:

- clear object homes
- plus a living front door that reflects active creative flow

## 2. Real-Life Usage Drafts

### Draft 1. User saves a strong first result and returns later

Goal:

- preserve something worth keeping
- find it again
- feel that it belongs to an evolving workflow life

What this demands:

- saved outputs must have a clear home
- Memory should not open as a cold filing cabinet

### Draft 2. User branches from a saved result

Goal:

- reopen an existing result
- make a variation
- keep both versions meaningful

What this demands:

- saved outputs must feel alive and reusable
- Memory should reflect lineage and revisitability

### Draft 3. User quick-saves a rough useful result

Goal:

- capture something now
- clean or promote it later

What this demands:

- rough captures need a real but lighter home
- they should not pollute the same area as fully keep-worthy saved work

### Draft 4. User intentionally browses reusable sources/context

Goal:

- find reusable shaping material for a new workflow

What this demands:

- reusable assets need their own clear home
- they should not feel like secondary clutter inside saved outputs

### Draft 5. User imports something from Community

Goal:

- take a discovered public object and make it part of personal Memory

What this demands:

- imported objects should become first-class personal objects
- but still preserve origin metadata

### Draft 6. Later continuity-linked traces

Goal:

- later recognize that some saved work or assets are tied to continuity entities

What this demands:

- continuity should enrich Memory
- but not dominate Memory structure in first-wave

These drafts strongly imply:

- Memory must distinguish major object types
- rough captures need their own lighter lane
- imports and continuity should enrich the structure, not fragment it

## 3. Candidate Structures

### Candidate A. Archive-Centric Structure

Shape:

- Recent
- Saved Prompts
- Prompt Sets
- Imports

Strengths:

- simple
- strongly tied to save/reuse

Weaknesses:

- too output-centric
- reusable sources/context feel bolted on
- too close to old Prompt Library thinking

### Candidate B. Library-Centric Structure

Shape:

- All Items
- Assets
- Saved Work
- Imports
- Identity Traces

Strengths:

- broad
- flexible

Weaknesses:

- too generic
- weak emotional meaning
- high risk of catch-all drift

### Candidate C. Object-Type Zoned Structure

Shape:

- Saved Work
- Reusable Assets
- Captures
- Imports

Strengths:

- clear homes for unlike objects
- strong practical clarity

Weaknesses:

- can feel static
- lacks a living front door
- risks becoming merely organized storage

### Candidate D. Flow-Based Memory Hub

Shape:

- Home / Continue
- Saved Work
- Reusable Assets
- Capture Inbox

Imports and continuity traces live inside the relevant sections.

Strengths:

- object clarity plus active-flow feeling
- strongest fit for living memory
- strong support for return use

Weaknesses:

- requires more discipline in Home so it does not become a noisy dashboard

### Candidate E. Heavy Unified Hub

Shape:

- one large smart home
- everything mostly discovered through filters and smart views

Strengths:

- modern
- flexible

Weaknesses:

- too abstract
- too dependent on perfect metadata behavior
- risks making Memory feel clever before it feels trustworthy

## 4. Candidate Comparison

### Why Candidate A loses

Because it is too close to output archive thinking and too weak for reusable assets.

### Why Candidate B loses

Because it is too library-generic and too likely to become a broad catch-all.

### Why Candidate C is close but loses

Because it has good object clarity, but not enough living-flow behavior for a realm that must feel active and reusable.

### Why Candidate E loses

Because it is too abstract and too dependent on smart views before the product has earned that complexity.

### Why Candidate D wins

Because it best combines:

- clear homes
- active reuse feeling
- fast re-entry
- strong save/capture distinction
- integrated imports
- and future enrichment headroom

## 5. Chosen Memory Structure

The chosen Memory structure is:

- **one recent-flow landing view**
- **two major object pillars**
- **one lighter capture lane**

That means:

### Default landing view

- `Memory Home`

### Major pillars

- `Saved Work`
- `Reusable Assets`

### Supporting lane

- `Capture Inbox`

This is the strongest first-wave structure because it gives Memory:

- a living front door
- durable object organization
- room for growth without catch-all collapse

## 6. Main Sections Inside Memory

## 6.1 Memory Home

Role:

- the living front door of Memory

Owns:

- recent work
- continue / branch / reopen shortcuts
- light surfacing of recent captures
- light surfacing of reusable assets
- important import arrivals

Does not own:

- deep object storage
- the full browse experience by itself

Memory Home should feel like:

- "what is alive in my creative memory right now?"

not:

- a productivity dashboard

## 6.2 Saved Work

Role:

- the home for kept workflow outputs

Owns:

- saved results
- branches / variants
- later grouping structures
- later continuity-linked saved results

Does not own:

- rough captures that are not yet worth keeping
- reusable shaping assets

Saved Work should feel like:

- preserved reusable outcomes

not:

- dead prompt records

## 6.3 Reusable Assets

Role:

- the home for reusable workflow-shaping material

Owns:

- transformed source libraries
- transformed workflow contexts
- starter bases
- reusable shaping ingredients
- imported public reusable shaping objects

Does not own:

- fully saved workflow outputs
- rough temporary captures

Reusable Assets should feel like:

- material that can shape future workflows

not:

- a separate co-equal app

## 6.4 Capture Inbox

Role:

- the home for rough, quickly saved, or not-yet-promoted useful results

Owns:

- Quick Save items
- rough external captures
- maybe unfinished worthwhile branches

Does not own:

- fully kept work
- major reusable assets

Capture Inbox should feel like:

- "worth looking at later"

not:

- failure
- or junk

This lane is important because it protects Saved Work from being polluted while keeping fast capture valuable.

## 7. Default Landing View Decision

The default landing view of Memory should be:

- **Memory Home**

Why:

- users need a living entry, not a storage wall
- Memory is a strong second pole, so it should greet the user with active meaning
- this supports returning use and reuse far better than landing directly inside a list

What Memory Home should show:

- continue recent work
- branch from strong saved work
- recent captures needing promotion or review
- reusable assets recently used or likely relevant
- recent imports from Community

The tone should be:

- active
- useful
- lightly guided

not:

- dashboard-heavy
- or analytics-heavy

## 8. Section Vs Lens Decisions

### True sections

These deserve their own sections:

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`

### Lenses / filters / metadata layers

These should **not** be primary first-wave sections:

- imported
- published
- continuity-linked
- branched
- recent

Why:

- these are better treated as qualities or views across real object homes
- promoting them to full sections would fragment Memory unnecessarily

So for example:

- an imported public workflow result lands in `Saved Work`
- an imported public source/context object lands in `Reusable Assets`
- both simply retain import origin metadata and filterability

## 9. Community Import Behavior

Imported public objects should land:

- **inside the correct object pillar**

That means:

- public saved outputs -> `Saved Work`
- public reusable shaping objects -> `Reusable Assets`

They should also carry:

- creator origin
- import date
- maybe public/private source badge

This is much stronger than having a separate `Imported` realm or section, because:

- imported objects become real members of personal Memory
- not temporary guests in a side area

## 10. Continuity-Trace Behavior

In first-wave Memory, continuity-linked traces should appear as:

- badges
- metadata
- filters
- relation cues inside existing objects

They should **not** become a primary Memory section yet.

Why:

- continuity is still a lighter realm in first-wave
- Memory should acknowledge continuity enrichment without letting it redefine the whole realm structure

So a saved result might later show:

- linked continuity entity
- continuity-aware lineage note

But it still remains inside `Saved Work`.

## 11. Workspace Connection Logic

Memory must connect back into Workspace very directly.

That means:

- reopen in Workspace
- branch into new Workspace session
- apply reusable asset into Workspace
- promote capture into Saved Work or Reusable Assets

The key rule is:

- Memory should always feel one step away from active creative use

It must never feel like:

- a separate dead zone the user has to "leave creation" to visit

The best mental model is:

- Workspace is where work happens now
- Memory is where useful work stays alive between nows

## 12. Strongest Risks

### 1. Memory Home becoming a dashboard junk room

This must stay tightly curated around active creative return/use, not analytics or noise.

### 2. Reusable Assets becoming too broad

If this section tries to hold every support concept without internal discipline, Memory will still become muddy.

### 3. Capture Inbox becoming a trash bin

It needs light dignity and promotion paths, not stigma.

### 4. Saved Work becoming passive archive again

It must support branch / reopen / reuse clearly.

### 5. Imported objects feeling second-class

They must land as real personal memory objects, not permanent outsiders.

### 6. Continuity traces becoming too visible too early

That would distort first-wave Memory and over-stage continuity maturity.

## 13. Final Recommendation

The strongest internal structure for `Memory` in MorpBase V2 is:

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`

with these deeper rules:

- Memory Home is the living front door
- Saved Work and Reusable Assets are the two true object pillars
- Capture Inbox is the lighter rough-memory lane
- imported and continuity-linked states remain lenses/metadata, not first-wave primary sections

The cleanest final sentence is:

- `Memory in MorpBase V2 should be a living hub with a recent-flow landing view, clear homes for saved work and reusable assets, and a lighter inbox for rough captures that are not yet fully promoted.`

That is the strongest current Memory structure for a complete MorpBase V2 without letting the realm collapse into either dead archive logic or broad catch-all library logic.
