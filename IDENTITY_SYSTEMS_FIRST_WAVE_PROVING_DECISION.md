# Identity Systems First Wave Proving Decision

## 1. Executive Conclusion

The best first proving lane is:

- **Character Identity with the larger realm explicitly preserved but not built**

That is stronger than:

- `Character Identity only` as an implied whole-realm stand-in
- `Character Identity + Outfit Identity` as a broader first wave
- a generic realm-scout implementation before any visible lane

The core reason is simple:

- `Character Identity` is still the clearest valid lane
- but it is only safe as a first move if it is explicitly framed as a **controlled proof inside the larger Identity Systems realm**

So the winning choice is not:

- `Character as the realm`

It is:

- `Character Identity as the first controlled proof of the Identity Systems realm, with later lanes such as Outfit Identity kept explicitly latent`

This gives MorpBase the strongest balance of:

- conceptual honesty
- real-world testability
- realm preservation
- product restraint

It also fits the current codebase and prototype situation best:

- the existing Character runtime can be mined for behavior and lane-level hints
- but the realm still stays conceptually larger than the current Character path

---

## 2. Controlled-Proof Standard

Under the locked translation decision, a valid first proving lane must satisfy all of these:

### 1. It must prove real continuity value

The lane must show that:

- a reusable continuity entity matters across workflows

### 2. It must preserve the realm boundary

The lane must not collapse identity into:

- Pools
- Territories
- Builder categories
- prompt fragments

### 3. It must stay larger than the prototype

The lane cannot simply inherit the current Character runtime as if it were already the architecture.

### 4. It must leave room for future lanes

The lane should prove one lane without pretending:

- Outfit
- Prop / Artifact
- Creature
- Group

have already been resolved or structurally committed.

### 5. It must not force premature realm exposure

A first lane can be visible without claiming:

- the full Identity Systems realm is already product-ready as a top-level surface

### 6. It must keep implementation danger bounded

The proving lane should not require MorpBase to build:

- a giant multi-lane framework
- a full relationship domain
- a public identity ecosystem
- a full continuity-universe architecture

That would be too much for a first proof.

---

## 3. What The First Lane Must Prove

The first lane must prove these things specifically.

### 1. That one reusable continuity entity class solves a real MorpBase gap

The lane must prove that:

- MorpBase does need a continuity layer above one workflow

### 2. That identity can be applied into Builder without Builder owning it

This is one of the most important tests.

### 3. That Prompt Preview can reveal identity as a legible live layer

The lane must show that identity can feel:

- clear
- active
- intentionally applied

not:

- hidden
- magical
- just another prompt snippet

### 4. That continuity can survive host variation

The lane must prove that the same entity can stay meaningful across:

- different Pools
- different Territories
- different Builder sessions

### 5. That the prototype behaviors translate into a valid lane without becoming the architecture

The lane must absorb the good behavioral lessons from the current Character prototype while rejecting its harder conceptual drift.

### 6. That archive-lineage grounding is at least believable

The lane does not need full lineage infrastructure immediately.
But it does need to remain grounded in the idea that:

- repeated real use and saved outputs can later refine the entity

---

## 4. What The First Lane Must Not Try To Prove Yet

The first lane should explicitly avoid trying to prove these things yet.

### 1. The full realm UI structure

It should not try to prove:

- top-level `Identity Systems` navigation

### 2. Multi-lane identity architecture in full

It should not try to prove:

- Character + Outfit + Prop together

### 3. Full relationship-domain logic

It should not try to prove:

- rich entity-to-entity relationship management

### 4. Full lineage infrastructure

It should not try to prove:

- complete saved-output tracing and refinement systems

### 5. Public discovery or publishing

It should not try to prove:

- community identity ecosystems
- profile-linked identity publication

### 6. The long-range continuity universe

It should not try to prove:

- Shared Storylines-level future continuity systems

The first lane must remain:

- lane proof

not:

- realm completion

## 5. Candidate First-Wave Lanes

### Candidate A: Character Identity only

This means:

- Character is the first lane, but without strong explicit language preserving the larger realm beyond it

### Candidate B: Character Identity with the larger realm explicitly preserved but not built

This means:

- Character is the proving lane
- the larger Identity Systems realm stays conceptually locked
- future lanes remain latent, acknowledged, and out of scope

### Candidate C: Character Identity + Outfit Identity

This means:

- MorpBase proves two parallel lanes at once

### Candidate D: Character Identity as a narrow pilot under low product exposure

This means:

- Character is still first, but the lane is kept especially restrained and underexposed

### Candidate E: A realm-scout lane that proves generic identity scaffolding before any visible lane

This means:

- build generic realm-facing structure or general identity scaffolding first
- defer committing to a visible lane until later

## 7. Best First Proving Choice

The best first proving choice is:

- **Character Identity with the larger realm explicitly preserved but not built**

This wins because it does four important things at once.

### 1. It uses the strongest existing lane

Character remains the clearest lane by:

- maturity
- user-value plausibility
- documentation strength
- prototype relevance

### 2. It preserves the larger realm honestly

It does not require MorpBase to pretend:

- Character is all of Identity Systems

### 3. It keeps the current Character prototype in its proper place

It allows:

- reuse of useful behaviors

while forbidding:

- prototype authority over the realm

### 4. It keeps the product disciplined

It allows a meaningful first proof without forcing:

- multi-lane rollout
- top-level realm exposure
- giant framework code

This is the strongest combination available right now.

---

## 8. Why The Other Options Should Wait

### Why raw `Character Identity only` should wait

Because without the realm-preservation clause, it is too easy to let Character become the whole realm by accident.

### Why `Character + Outfit` should wait

Because two lanes at once would:

- overgrow the first proof
- raise architecture costs
- blur what was actually proven first

### Why a purely narrow hidden pilot should wait as the main framing

Because it is excellent as a restraint, but too weak as the actual conceptual choice.

The winning lane should still be defined positively, not only conservatively.

### Why generic realm-scout scaffolding should wait

Because MorpBase still needs:

- a visible and valid lane proof

not:

- generic infrastructure before proven user value

## 9. What Must Remain Explicitly Out Of Scope

For the winning lane, these things must stay explicitly out of scope.

### 1. Outfit Identity implementation

Keep it conceptually preserved, not built.

### 2. Prop / Artifact, Creature, and Group lanes

Preserve them as future candidates only.

### 3. Full relationship-domain behavior

Do not let the first lane balloon into a broader identity graph system.

### 4. Top-level `Identity Systems` product exposure

Do not let one lane force a full realm nav decision.

### 5. Full archive-lineage infrastructure

Keep the rule, not the whole system.

### 6. Community publishing / discovery

Out of scope.

### 7. Generic multi-lane framework code

Do not build a huge future-proof shell before the first lane proves itself.

---

## 10. How To Preserve The Larger Realm While Proving One Lane

This is the most important control problem.

### Rule 1

Always frame the lane as:

- `Character Identity` is the first proving lane inside the future `Identity Systems` realm

Never as:

- `Character Identity is Identity Systems for now`

### Rule 2

Keep future lanes named but latent.

This prevents forgetfulness without overcommitting.

### Rule 3

Treat current Character code as:

- prototype material

not:

- realm authority

### Rule 4

Do not let lane-specific projection rules become the full projection architecture automatically.

### Rule 5

Do not let lane-specific local storage or CRUD become the assumed realm persistence architecture.

### Rule 6

Document realm truth, lane truth, and prototype truth separately in all future planning.

### Rule 7

Use low-to-moderate product exposure for the first lane.

That means:

- enough visibility to test real use
- not enough visibility to imply full realm maturity

## 11. How The Current Character Prototype Should Be Treated Under The Winning Lane

Under the winning lane, the current Character prototype should be treated as:

- **behaviorally useful**
- **architecturally provisional**
- **conceptually subordinate to the realm**

### Preserve conceptually

- Prompt Preview apply / change / remove pattern
- library / application split
- narrow active session reference
- lane-level entity structure as one example

### Treat as provisional

- `activeCharacterId` as the final session contract
- `'character'` as the final prompt projection contract
- direct phrase injection as the final architecture
- the current modal as the final management surface

### Do not let it dictate

- realm meaning
- final persistence shape
- final realm visibility timing
- multi-lane future structure

This is the cleanest controlled-proof use of the prototype.
