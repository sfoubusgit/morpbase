# MorpBase V2 Experience Prototyping Plan

## 1. Executive Conclusion

The V2 prototype phase should be:

- **selective**
- **experience-led**
- **sequence-based**

It should not try to prototype the whole product at once.

The strongest prototype program for V2 is:

1. **core first-use Workspace slice**
2. **Memory continuation slice**
3. **Community circulation slice**
4. **Continuity activation slice**
5. **shell / hierarchy slice**

The most important judgment is:

- V2 is now ready to move into experience prototyping
- but only if the prototype phase stays tightly focused on validating the strongest product feels

## 2. Real-Life Prototype-Validation Journeys

### Journey 1. New user reaches meaningful first success fast enough

Question:

- does the product let a new user feel MorpBase quickly enough?

What the prototype must prove:

- the user understands where to act
- the guided first-flow layer helps without over-teaching
- `Prompt Preview` builds trust fast
- the first keep/save moment feels earned and meaningful

### Journey 2. Memory really feels like a second pole, not a library

Question:

- does the product truly feel built around `Workspace + Memory`, or does Memory still read like storage?

What the prototype must prove:

- saved work feels alive
- branch/reopen/use actions feel central
- Memory -> Workspace movement feels like continuation, not admin

### Journey 3. Public circulation feels integrated, not bolted on

Question:

- does Community actually feel like part of MorpBase’s core object loop?

What the prototype must prove:

- publishing from Memory feels natural
- discovering public objects feels useful
- importing back into Memory feels like real adoption into practice

### Journey 4. Continuity feels meaningful without becoming too heavy

Question:

- can Continuity matter in first-wave without over-expanding its role?

What the prototype must prove:

- the user understands what a recurring entity is for
- appearances/recurrence are concrete enough
- activation into Workspace makes immediate sense

### Journey 5. The shell preserves hierarchy in lived experience

Question:

- does the product actually feel asymmetrical in use, not just in documents?

What the prototype must prove:

- Workspace feels central
- Memory feels strong
- Community feels real but not default
- Continuity feels visible but lighter

These journeys show that the prototype program should validate:

- center strength
- Memory strength
- transition quality
- public-loop legitimacy
- and disciplined Continuity

## 3. Prototype-Worthy Slices

### Slice 1. Core First-Use Workspace

Includes:

- direct entry into Workspace
- guided first-flow layer
- guided authoring block rhythm
- live Prompt Preview response
- first keep/save handoff

Why it matters:

- this is the strongest make-or-break slice of the whole product

### Slice 2. Memory Continuation

Includes:

- arrival after first keep/save
- Memory Home feel
- viewing Saved Work
- branch/open/use actions
- return into Workspace

Why it matters:

- this validates the strongest second pole and the product’s reuse promise

### Slice 3. Community Circulation

Includes:

- publish from Memory
- Discover scanning
- public object open path
- import back into Memory

Why it matters:

- this validates whether Community is truly integrated into the object loop

### Slice 4. Continuity Activation

Includes:

- Continuity Home
- entity browse/select
- appearance understanding
- activate into Workspace

Why it matters:

- this validates whether Continuity is concrete enough and properly weighted

### Slice 5. Shell / Hierarchy

Includes:

- realm switching
- active-state emphasis
- primary vs secondary-visible weighting
- context preservation across transitions

Why it matters:

- this validates the whole-product feel beyond any single screen

## 4. Prototype Goals By Slice

### Core First-Use Workspace

Should validate:

- first-use clarity
- time-to-value
- trust through Preview
- meaningful first success

Success looks like:

- the user can start fast
- the workspace feels guided but not rigid
- saving feels like a natural completion of creative work

Failure looks like:

- onboarding feels lecture-like
- the workspace feels like a questionnaire
- the keep/save moment feels detached or weak

### Memory Continuation

Should validate:

- Memory as a living second pole
- branch/reopen/use as strong actions
- continuity of work across sessions

Success looks like:

- Memory feels active and valuable
- the user wants to continue from it

Failure looks like:

- Memory feels archival only
- return-to-Workspace feels hidden or mechanical

### Community Circulation

Should validate:

- public/private loop clarity
- public object usefulness
- import/publish legitimacy

Success looks like:

- Community feels meaningfully downstream from private work
- importing feels useful, not ornamental

Failure looks like:

- Community feels detached
- Discover feels like a browse wall without product consequence

### Continuity Activation

Should validate:

- continuity entity meaning
- appearances/recurrence legibility
- activation as a clean transition into live work

Success looks like:

- the user understands why Continuity exists
- activation changes Workspace meaningfully without overloading it

Failure looks like:

- Continuity feels abstract
- activation feels like extra setup with unclear payoff

### Shell / Hierarchy

Should validate:

- asymmetry in lived navigation
- calmness
- realm legitimacy without flattening

Success looks like:

- Workspace and Memory feel like the main lived product
- Community and Continuity feel real without competing equally

Failure looks like:

- the product feels like equal tabs again
- or secondary realms feel hidden/decorative

## 5. Prototype Fidelity Strategy

### Low-fidelity structural prototypes

Best for:

- shell hierarchy
- first-use path shape
- cross-screen transition logic
- realm exposure rules

Purpose:

- validate structure and movement before styling pressure enters

### Medium-fidelity interaction prototypes

Best for:

- Workspace flow
- Memory continuation behaviors
- publish/import loops
- continuity activation

Purpose:

- validate interaction rhythm and object handoffs

### Higher-fidelity visual/product prototypes

Best for:

- shell atmosphere
- first-use Workspace feel
- Memory mood shift
- Community energy without feed chaos
- Continuity tone

Purpose:

- validate whether the design-universe direction actually strengthens the product

Rule:

- do not start with high-fidelity everywhere
- increase fidelity where behavior is already structurally sound and visual feel matters

## 6. Prototype Program Sequence

### Phase A. Structural validation

Prototype:

- shell / hierarchy
- Workspace first-use path
- Workspace -> Memory transition

Goal:

- validate the strongest center and second-pole logic first

### Phase B. Continuation validation

Prototype:

- Memory continuation slice
- branch/open/use return to Workspace

Goal:

- prove that Memory is truly a second pole

### Phase C. Public-loop validation

Prototype:

- publish from Memory
- Discover
- import back into Memory

Goal:

- prove that Community is integrated, not decorative

### Phase D. Continuity validation

Prototype:

- entity browse/select
- appearances
- activate into Workspace

Goal:

- prove that Continuity is meaningful and correctly weighted

### Phase E. Higher-fidelity synthesis

Prototype:

- a small stitched journey across shell, Workspace, Memory, Community, and Continuity

Goal:

- test whether the whole product feels like one product

## 7. Success / Failure Signals

### Success signals

- users can reach first value quickly
- Memory feels essential, not passive
- public circulation feels useful and integrated
- Continuity feels meaningful but not bloated
- the shell hierarchy is felt, not just intellectually understood
- the design universe strengthens product identity without harming clarity

### Failure signals

- first-use still feels too complex or too tutorial-like
- Memory still behaves like storage
- Community still feels bolted on
- Continuity still feels abstract or premature
- the shell still feels like equal destinations
- stronger visual direction begins to obscure behavior or hierarchy

## 8. Readiness Judgment

V2 is now:

- **ready to begin experience prototyping directly**

No additional broad product-preparation layer is required before prototypes.

What still matters:

- prototype discipline
- not prototyping everything
- and using the prototype phase to validate, not reopen, the foundation by default

## 9. Final Judgment

The strongest V2 prototype program is:

- **a selective, phased prototype sequence that validates the first-use Workspace experience first, the Memory continuation loop second, the Community circulation loop third, the Continuity activation model fourth, and the whole-product hierarchy through a stitched synthesis pass last**

That is the cleanest way to test whether MorpBase V2 is truly ready for implementation planning without letting prototyping become another round of unfocused exploration.
