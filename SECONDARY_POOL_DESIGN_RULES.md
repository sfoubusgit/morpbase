# Secondary Pool Design Rules

## Purpose

This document defines what a Secondary Pool should be inside MorpBase.

It exists to protect the distinction between:

- main pools as identity anchors
- secondary pools as compatible variation layers

This distinction is important because the product is becoming increasingly compositional. Without clear rules, secondary pools could easily become confusing duplicates of main pools.

## Core Definition

A Secondary Pool is a reusable variation layer that is meant to be combined with a stronger host workflow.

It is not supposed to define the full image family by itself.

Its job is to:

- add controlled variation
- introduce a narrower theme or material system
- increase iteration possibilities within an existing host workflow
- remain compatible with a family of nearby main pools

## What A Secondary Pool Is

A Secondary Pool is:

- additive
- modular
- narrower than a main pool
- meant to sit on top of a stronger host identity
- ideally reusable across a host family

Examples of good secondary-pool roles:

- portrait accessory systems
- symbolic motif systems
- handheld object families
- ornament families
- mood-specific effect layers
- decorative framing layers

## What A Secondary Pool Is Not

A Secondary Pool is not:

- a full workflow center
- a replacement for a main pool
- a hidden duplicate of a main pool
- a generic dump of unrelated items
- a new Mode in disguise

If a pool is trying to define:

- the full style family
- the core composition family
- the main baseline identity
- the dominant workflow anchor

then it is probably not a secondary pool anymore.

## Relationship To Main Pools

The cleanest model is:

- main pool = identity anchor
- secondary pool = variation layer

A main pool should be able to function meaningfully on its own.
A secondary pool usually should not need to do that.

This means a secondary pool is strongest when:

- it assumes a host family already exists
- it adds a controlled dimension of change
- it does not compete for baseline ownership

## Compatibility Rule

A good secondary pool should usually be compatible with a **family of nearby main pools**, not just one single host.

That does not mean it must be universal.

The best pattern is:

- one or more primary best-fit hosts
- several adjacent compatible hosts
- obvious weak-fit or non-fit hosts

Example:

A portrait-oriented secondary pool should ideally work with many portrait-family main pools, not just one exact pool.

This gives MorpBase stronger composability without making pools vague or generic.

## Host-Family Principle

Secondary pools should usually be broad **within a host family**, not broad across the entire app.

For example:

- a portrait accessory pool should work across many portrait hosts
- it does not need to work for environments, mechs, objects, and landscapes

That is the healthiest middle ground between:

- over-specialized one-host-only pools
- weak universal pools

## IDP Rule

Secondary pools should generally **not** have IDPs.

Why:

- IDPs are for identity anchoring
- main pools are the right place for identity anchoring
- secondary pools are supposed to be additive

If a secondary pool gains strong IDPs, it risks becoming:

- another main pool
- a competing baseline system
- a source of prompt identity conflict

So the default rule should be:

- main pools may have IDPs
- secondary pools usually should not

If a secondary pool ever needs stronger internal variation, prefer lighter mechanisms first, such as:

- strong section structure
- curated initiative phrases
- grouped item families
- compatibility notes

## Initiative Phrase Rule

A secondary pool may have initiative phrases in some cases, but they should be used carefully.

If used at all, they should:

- support the pool’s variation role
- not try to replace the host identity
- remain clearly subordinate to the main pool baseline

This means initiative phrases for a secondary pool should be:

- lighter
- more scoped
- less identity-defining

than initiative phrases in a main pool.

## Structural Shape

A secondary pool should usually be narrower than a main pool.

That often means:

- fewer sections
- tighter section scope
- denser thematic coherence

A main pool might carry:

- subject
- style
- lighting
- mood
- composition
- effects

A secondary pool might only need:

- props
- effects
- mood

or:

- props
- style
- effects

or:

- objects
- materials
- effects

The point is: it should cover the variation layer it owns, not everything.

## Good Secondary Pool Test

A candidate secondary pool is probably valid if:

1. it adds one clear dimension of variation
2. it does not try to redefine the whole image family
3. it can combine with multiple nearby main pools
4. it remains useful as a modular extension
5. it does not require its own Mode
6. it does not strongly need IDPs to make sense

If those do not hold, the pool may instead be:

- a main pool
- a pool that should be merged into a main pool
- a weak idea that is too broad or too narrow

## Example Reading

For `Celestial Pixel Portrait`, good secondary pool ideas might be:

- celestial hair ornaments
- sacred emblems and relics
- occult crescent accessories
- idol ribbon and jewel accents

These work because they:

- extend the host family
- create readable variation
- do not redefine the core portrait identity

## Final Product Rule

Secondary Pools should be treated as **reusable compatible variation layers**, not as smaller main pools.

That means:

- they should usually work across a host family
- they should generally not have IDPs
- they should extend a stronger workflow center rather than compete with it

## Final Summary

A strong Secondary Pool is:

- narrower than a main pool
- compatible with multiple nearby hosts
- modular
- additive
- identity-supporting, not identity-owning

That is the cleanest and healthiest rule set for MorpBase.
