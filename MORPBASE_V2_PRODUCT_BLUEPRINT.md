# MorpBase V2 Product Blueprint

## 1. Executive Conclusion

The strongest first-wave product blueprint for MorpBase V2 is:

- **one workflow-centered product with four major screen families, asymmetric top-level access, and object-driven transitions**

The blueprint must be read through one core law:

- `Workspace` is the dominant center
- `Memory` is the strongest second pole
- `Community` is a real but intentional public destination
- `Continuity` is a real but lighter support realm

So the blueprint should not become:

- a flat realm map turned into equal pages
- a dashboard-centered product
- or a set of disconnected verticals

It should become:

- one connected product whose screen families reinforce a shared creative object flow

The most important blueprint consequence is:

- the next V2 phase should focus on **interaction blueprinting inside these screen families**
- not on reopening major product-structure debates

## 2. Real-Life Blueprint Journeys

### Journey 1. First-time user enters Workspace, creates, and keeps a result

Goal:

- feel MorpBase quickly
- understand where to act
- reach a real save-worthy success

What this demands:

- `Workspace` must open directly into the true product center
- the guided first-flow layer must live inside the real Workspace
- the first meaningful outcome must hand naturally into `Memory`

### Journey 2. Returning user branches from Memory into Workspace

Goal:

- continue real work through reuse

What this demands:

- `Memory` must be structurally strong, not a side library
- saved work and reusable assets must both support return movement into `Workspace`
- branch/reopen/use actions must be central to the Memory blueprint

### Journey 3. User activates a continuity entity into a live workflow

Goal:

- use recurring sameness across work without turning Workspace into a continuity editor

What this demands:

- `Continuity` must have its own realm home
- activation into `Workspace` must be a primary continuity transition
- continuity truth must remain outside the active workflow surface

### Journey 4. Creator publishes from Memory into Community

Goal:

- move from private value into public circulation naturally

What this demands:

- `Publishing` must be strongly linked to kept/private objects
- `Memory` must expose publish-worthy objects
- `Community` must feel downstream from real work, not parallel to it

### Journey 5. User discovers something in Community and imports it back into Memory

Goal:

- make public circulation feel useful, not ornamental

What this demands:

- public object pages and cards must clearly support import/use
- imported objects must land in the correct Memory pillar
- Community -> Memory must feel like a central product transition

These journeys confirm:

- the blueprint succeeds only if its transitions are object-driven and realm boundaries remain legible

## 3. Frozen Foundation Restated For Blueprinting

The frozen V2 foundation becomes this blueprint problem:

- how do we turn one asymmetrical product into a navigable first-wave structure without flattening it?

The blueprint must preserve:

- the `Workspace + Prompt Preview` center
- `Memory` as the second pole
- `Continuity` as lighter but real
- `Community` as downstream public circulation
- direct-to-workspace first-use
- asymmetric shell behavior

The blueprint must **not** reopen:

- whether V2 is a new product
- whether Workspace is the center
- whether Memory is essential
- whether Continuity or Community deserve realm-level existence

Those are now foundation truths.

## 4. Major Screen Families

## 4.1 Workspace

### Purpose

- own the live creative session
- let the user shape, see, refine, and keep a result

### Primary objects

- active workflow session
- live prompt output
- active context influences

### Major sections

- workspace shell
- guided authoring column
- persistent Prompt Preview column
- keep/save handoff
- contextual support entry points

### Key entry paths

- default product entry
- return from `Memory`
- activation entry from `Continuity`
- later branch/reuse entry from `Community` imports

### Key outgoing transitions

- `Workspace -> Memory`
- contextual support access into reusable assets
- later contextual continuity usage

### Blueprint note

- support systems should enter Workspace contextually, not as competing sub-centers inside it

## 4.2 Memory

### Purpose

- keep, organize, reopen, branch, and feed future work

### Primary objects

- saved workflow outputs
- reusable workflow-shaping assets
- rough captures
- imported public objects

### Major sections

- `Memory Home`
- `Saved Work`
- `Reusable Assets`
- `Capture Inbox`

### Key entry paths

- from shell
- from successful keep/save in Workspace
- from public import in Community

### Key outgoing transitions

- `Memory -> Workspace` via reopen/branch/use
- `Memory -> Community` via publish
- `Memory -> Continuity` via continuity-linked work exploration

### Blueprint note

- imported public objects should resolve into `Saved Work` or `Reusable Assets`, not into a separate imported zone

## 4.3 Continuity

### Purpose

- stabilize recurring sameness across work
- own recurring entities and their appearances through kept work

### Primary objects

- continuity entities
- continuity-linked appearances through work

### Major sections

- `Continuity Home`
- `Entities`
- `Appearances`

### Key entry paths

- from shell
- from continuity-linked work in Memory
- from contextual activation needs in Workspace

### Key outgoing transitions

- `Continuity -> Workspace`
- `Continuity -> Memory`
- later `Continuity -> Community` only through continuity-enriched public objects

### Blueprint note

- first-wave Continuity should feel real and useful, but smaller and more disciplined than Memory or Community

## 4.4 Community

### Purpose

- circulate MorpBase creative objects publicly
- connect creators, public objects, and reuse

### Primary objects

- public workflow results
- public reusable assets
- creator public practice surfaces

### Major sections

- `Discover`
- `Creators`
- `Publishing`

### Key entry paths

- from shell
- from publish intent in Memory

### Key outgoing transitions

- `Community -> Memory` through import/adopt
- `Community -> deeper public object pages`
- `Community -> creator pages`

### Blueprint note

- Community must remain downstream from private creation and strongly tied to object flow

## 4.5 Profile

### Purpose

- handle account and private creator controls

### Primary objects

- account identity
- settings
- private public-presence controls

### Major sections

- account/settings
- creator/account controls

### Key entry paths

- utility shell access

### Key outgoing transitions

- mostly return to current working realm

### Blueprint note

- Profile must not become a co-equal product realm

## 5. Cross-Product Object Flow

The product blueprint should be read through these object movements:

### 1. Active workflow session

Path:

- born in `Workspace`
- shaped there
- previewed there
- then either discarded, kept, or later branched from

### 2. Saved work

Path:

- created in `Workspace`
- kept into `Memory`
- reopened or branched back into `Workspace`
- optionally published into `Community`

### 3. Reusable assets

Path:

- stored in `Memory`
- used to shape new workspace sessions
- optionally published into `Community`
- public reusable assets can also be imported back into Memory

### 4. Continuity entities

Path:

- owned in `Continuity`
- activated into `Workspace`
- traced across kept work in `Memory`
- later enrich public objects in `Community`

### 5. Public workflow results

Path:

- released from private value into `Community`
- discovered publicly
- opened, followed, or imported back into private use

### 6. Public reusable assets

Path:

- released from reusable personal value into `Community`
- discovered publicly
- imported into `Memory`
- used in future workspace sessions

This object flow is the main reason the product remains one product instead of several connected tools.

## 6. Top-Level vs Contextual Access

### Top-level shell access

These screen families are directly enterable from the shell:

- `Workspace`
- `Memory`
- `Community`
- `Continuity`
- `Profile`

But with hierarchy:

- primary-visible:
  - `Workspace`
  - `Memory`
  - `Community`
- secondary-visible:
  - `Continuity`
- utility:
  - `Profile`

### Contextual access

These transitions should often matter more than pure shell entry:

- `Workspace -> Memory`
- `Memory -> Workspace`
- `Memory -> Community`
- `Community -> Memory`
- `Continuity -> Workspace`
- `Memory -> Continuity`

### Background / supportive access

These should be present through contextual entry or supportive exposure rather than as separate major screens:

- support/context use inside Workspace
- continuity-linked cues inside Memory
- public-object creator context inside Community

This keeps the blueprint from over-expanding screen count.

## 7. Primary Transitions

The blueprint should structurally privilege these movements:

### 1. Workspace -> Memory

Meaning:

- keep what matters

This is the strongest success transition in the product.

### 2. Memory -> Workspace

Meaning:

- branch, reopen, continue

This is the strongest return transition in the product.

### 3. Memory -> Community

Meaning:

- publish what deserves public life

This is the strongest private-to-public transition.

### 4. Community -> Memory

Meaning:

- import/adopt into personal practice

This is the strongest public-to-private transition.

### 5. Continuity -> Workspace

Meaning:

- activate recurring sameness in live work

This is the strongest continuity transition.

### 6. Memory -> Continuity

Meaning:

- understand recurrence through kept work

This is an important secondary transition.

## 8. Blueprint Risks

### Risk 1. Screen inflation

If blueprinting keeps turning every structural distinction into a separate screen family, the product will become too broad.

### Risk 2. Context loss between realms

If movement between screen families does not preserve object context, the product will feel fragmented.

### Risk 3. Continuity over-weighting

If Continuity's screen family becomes too heavy too early, the asymmetrical hierarchy breaks.

### Risk 4. Community detachment

If Publishing/import flows are not tightly tied to Memory objects, Community will feel bolted on.

### Risk 5. Workspace sub-center drift

If support systems inside Workspace become too visible too early, the main center will weaken again.

## 9. Readiness For Interaction Blueprint

The product blueprint is now strong enough to proceed into **interaction blueprint** work.

Why:

- the major screen families are now clearly owned
- the object flow is explicit
- top-level vs contextual access is defined
- primary transitions are clear

What interaction blueprint should tackle next:

- exact workspace first-use state
- block/phase interaction behavior
- Memory reopen/branch/use flows
- publish/import interaction details
- continuity activation behavior
- shell active-state behavior

## 10. Final Judgment

The strongest V2 product blueprint is:

- **an asymmetric, screen-structural product centered on Workspace, reinforced by Memory, extended intentionally through Community, supported by a lighter Continuity realm, and tied together by one shared creative object flow**

That is now strong enough to stop broad product-structure exploration and move into interaction blueprint work.
